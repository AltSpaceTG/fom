# FAQ

#### Чем это отличается от кэша или планировщика задач?

Кэш хранит значения, которые можно пересчитать по требованию; FOM хранит
*процессы*, состояние которых дорого строить и которое восстанавливается через
`load` (дёшево), а не `init` (дорого), после рестарта. Планировщик задач запускает
задачи по часам; FOM держит долгоживущее, запрашиваемое состояние и реактивно
переинициализирует его при смене зависимостей. Ближайшая модель — «небольшой граф
долговечных, самовосстанавливающихся read-моделей».

#### Должно ли моё состояние помещаться в память?

*Живой* объект, который производит `load`, живёт в памяти и отвечает на запросы;
*сохранённая* форма — это ячейки `byte[]` в логе. Если состояние огромно,
сохраняйте компактный дескриптор, а `load` пусть строит структуру, которая
стримит или подгружает страницами извне — держите `load` быстрым, тяжёлую работу
откладывайте на первый `compute`.

#### Что если `init` всё время падает?

Он повторяется с экспоненциальным backoff, пока не исчерпан общий бюджет
`initTimeout`, затем процесс уходит в `Dead` с
`InitializationTimeoutException`. Исключение: если бэкенд лога отказывается
сохранить результат init (например, он превышает лимиты полезной нагрузки
лога), процесс сразу уходит в `Dead` без повторов. `load`, который продолжает падать, откатывается
к свежему `init`; если он снова падает на этом свежем состоянии, следующие откаты
идут с backoff и делят тот же бюджет, после чего процесс уходит в `Dead`.
`trigger` перезапускает процесс в `Dead`. См.
[Жизненный цикл процесса](concepts/process-lifecycle.md).

Падающий **reinit** обходится дешевле: по умолчанию (`ReinitStrategy.KEEP_OLD`)
старая версия отвечает на запросы, пока инициализируется новая, и продолжает
обслуживать, если новая не удалась. Узел тогда помечен `stale`, наблюдатель
получает `onReinitFailed`, а reinit сам повторяется через
`reinitRetryBackoffMin` (если причина не постоянная). Чтобы остановить reinit,
который продолжает падать, вызовите `engine.cancelInit(name)`: он отменяет
идущую попытку или запланированный повтор, узел продолжает обслуживать,
остаётся `stale` и автоматически не повторяется — его переинициализирует
следующий `trigger` или старт (запрос, уже стоявший в очереди за отменённой
попыткой, запускается сразу). При `RELEASE_FIRST` старое
состояние снимается *до* запуска нового `init`, поэтому неудавшийся reinit
оставляет узел в `Dead` без состояния — см.
[Если reinit не удался](concepts/process-lifecycle.md#when-a-re-init-fails).

#### Мой `init` ходит в API с rate limit (HTTP 429, `Retry-After`) — как выдержать паузу?

[Backoff](concepts/process-lifecycle.md#backoff) повторов движка —
**общий для всего движка** (`EngineConfig.backoffMin` / `backoffMax`, одинаковые
для всех узлов) и ничего не знает о вашем внешнем сервисе: он **игнорирует
`Retry-After`**, поэтому следующая попытка может прийти раньше, чем разрешает
сервис (и потратить ещё одну попытку на 429), или намного позже. Обрабатывайте
rate limit внутри `init`:

- **соблюдайте `Retry-After` в `init`** — поспите и повторите вызов, но только
  пока ожидание укладывается в лимит, который вы держите заметно ниже
  `initTimeout`. Бюджет покрывает *все* попытки и их backoff, а `init` не
  может узнать, сколько от него осталось, — поэтому ведите свой дедлайн;
- иначе **падайте сразу** — бросьте исключение, и backoff движка повторит
  попытку в пределах бюджета.

Никогда не ждите дольше бюджета init: когда он исчерпан, попытка окончена
(поздний результат отбрасывается), и узел уходит в `Dead` с
`InitializationTimeoutException`.

```java
static final Duration MAX_RATE_LIMIT_WAIT = Duration.ofSeconds(10);  // заметно меньше initTimeout

@Override
public CompletionStage<Map<String, byte[]>> init(QueryableContext ctx) {
    long giveUpAt = System.nanoTime() + MAX_RATE_LIMIT_WAIT.toNanos();
    while (true) {
        HttpResponse<byte[]> rsp = fetch();                       // ваш HTTP-вызов
        if (rsp.statusCode() != 429) {
            return CompletableFuture.completedFuture(Map.of("data", rsp.body()));
        }
        Duration wait = retryAfter(rsp).orElse(Duration.ofSeconds(1)); // заголовок разбираете сами
        if (System.nanoTime() + wait.toNanos() > giveUpAt) {
            // Не укладывается: проваливаем попытку; backoff движка повторит её в пределах бюджета.
            throw new InitializationException("rate limited, Retry-After " + wait);
        }
        try {
            Thread.sleep(wait);                                    // init выполняется в своём виртуальном потоке
        } catch (InterruptedException e) {                         // остановка или cancelInit
            Thread.currentThread().interrupt();
            throw new InitializationException("interrupted while rate limited", e);
        }
    }
}
```

#### Можно ли запускать больше одного экземпляра?

Да, с `PostgresLogBackend`: один становится лидером (advisory-lock); остальные
быстро падают при конструировании и могут встать в standby. См.
[Несколько узлов](guides/multi-node.md). Файловый и in-memory бэкенды —
однопроцессные.

#### Могут ли два `Engine` делить один экземпляр `LogBackend`?

Нет — **один `Engine` на экземпляр бэкенда**. Ничто не мешает передать тот же
объект бэкенда второму `Engine`, но его первый `newGraph` захватывает лидерство
в логе (дописывает свой `LogLeader`). С этого момента записи первого движка
отклоняются — его триггеры, переинициализации и изменения графа падают с
`LeadershipLostException`, — а его процессы **продолжают отдавать состояние,
которое держат в памяти** и которое больше не следует за логом. На пути
запросов ничего не падает, поэтому первый движок молча отдаёт устаревшее
состояние; увидеть это можно только в `introspect().isLeader()`. Для второго
движка заведите отдельный лог (файл, таблицу), а для standby см.
[Несколько узлов](guides/multi-node.md).

#### Как запускать под менеджером сервисов (systemd, Kubernetes)?

fom **не регистрирует shutdown hook** в JVM — это библиотека, и жизненным
циклом процесса управляете вы. Зарегистрируйте свой, который закрывает движок, а
затем бэкенд лога (движок никогда не закрывает переданный ему бэкенд):

```java
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    engine.close();     // останавливает процессы, сначала потребителей
    backend.close();    // освобождает блокировку файла / соединение с БД
}));
```

Если `close()` вызван дважды одновременно — скажем, shutdown hook и
try-with-resources, — второй вызов **ждёт**, пока первый не закончит
останавливать процессы, и только потом возвращается. Поэтому закрывать бэкенд
сразу после возврата вашего `close()` безопасно, какой бы вызов ни вернулся
первым. Сразу, без взаимоблокировки, возвращается только `close()`, вызванный
в том самом потоке, который выполняет первый `close()`, и вызванный на
диспетчере процесса (см. ниже). Любой другой поток ждёт — в том числе колбэк
`EngineObserver`, выполняющийся не на диспетчере. Колбэки выполняются в **потоках
движка**, и в каком именно — зависит от колбэка и момента: в диспетчере
процесса, в его init/load-воркере или сторожевом потоке бюджета (`onInitFailed`,
например, вызывается из всех трёх) или в потоках наблюдателя движка, — никогда
не рассчитывайте на конкретный. `close()` в колбэке, который оказался на
диспетчере процесса, сразу бросает `IllegalStateException` («close() called on
the dispatcher of 'X' (from an EngineObserver callback about it); call it from
another thread»), а не блокирует
этот диспетчер, — если только движок уже не закрывается: тогда он просто
возвращается. Если колбэку действительно нужно запустить остановку, используйте
`Thread.startVirtualThread(engine::close)`.

У «безопасно» есть одно ограничение — зависший бэкенд. `close()` ждёт
поставленные в очередь записи каждого процесса в лог не дольше
`cleanupTimeout`; после этого он логирует `WARN` «FSM[X] log writes still
pending after …; not waiting for them any longer» и возвращается. Застрявшая
запись может попасть в лог и после возврата `close()` (или упасть на уже
закрытом бэкенде). Если она попала, это корректная запись, и следующий старт
обработает её как любую другую — см.
[Жизненный цикл процесса](concepts/process-lifecycle.md#повторы-backoff-таймауты).

Не вызывайте `close()` из колбэка `EngineObserver`, из `cleanUp` или из проверки
watcher'а. Некоторые колбэки выполняются в потоке идущего `newGraph`,
`updateGraph` или `remove` (например, `onProcessRemoved`): `close()`
там останавливает движок прямо под этим вызовом, и он падает с «Engine closed
while 'X' was starting», хотя вызывающий ничего не закрывал. Вместо этого
подайте сигнал своему коду завершения.

То же правило — для любого вызова control plane, который **останавливает
процесс** (`pause`, `remove`, `TenantAwareEngine.pauseTenant` /
`removeTenant`, `newGraph` / `updateGraph`, который его убирает или
переопределяет), сделанного синхронно из колбэка наблюдателя об **этом же
процессе**: колбэк может выполняться на его диспетчере, а остановка ждала бы
именно этот диспетчер. Движок сразу отказывает в таком вызове с
`IllegalStateException` («… called on that process's own dispatcher …») — до
взятия управляющей блокировки и ничего не меняя.

Вызовы, затрагивающие только другие процессы, разрешены — если только в этот
момент управляющую блокировку не держит **другой** вызов control plane (первый
`newGraph` держит её, пока ждёт, что все узлы дойдут до `Serving`). Тогда любой
вызов control plane из колбэка на диспетчере процесса — `newGraph`,
`updateGraph`, `updateConfig`, `remove`, `pause`, `resume`, `resumeUnblocked` —
сразу бросает `IllegalStateException` («…(...) called from an EngineObserver
callback while another control-plane call is in progress; call it from another
thread»), а не блокируется; раньше диспетчер висел весь бюджет старта, и первый
`newGraph` падал. Движок логирует и проглатывает исключение, как любой сбой
колбэка, — так что вызов молча не выполняется. Передавайте вызовы control plane
другому потоку, например
`Thread.startVirtualThread(() -> engine.pause(Set.of(name)))`. См.
[Остановка процесса из колбэка](guides/observability.md#stopping-from-a-callback).

`close()` останавливает процессы одной глубины зависимостей вместе, каждый с
`cleanupTimeout`, поэтому может занять до **(число уровней зависимостей)
× `cleanupTimeout`**. Дайте таймауту остановки менеджера сервисов
(`TimeoutStopSec` в systemd, `terminationGracePeriodSeconds` в Kubernetes) не
меньше. Если JVM всё же убьют (`SIGKILL`) посреди `close()`, ничего не
потеряется: штатная остановка не пишет `LogDead`, поэтому следующий старт, как
обычно, загрузит все процессы тёпло, а записанные, но ещё не применённые
триггеры будут воспроизведены. См.
[Идемпотентный рестарт](concepts/idempotent-restart.md).

#### Как понять, что граф успокоился, перед остановкой?

`introspect()` показывает не всё, что ещё предстоит. Re-init, запрошенный
`trigger` или шагом [реактивного каскада](concepts/reactive-cascade.md), сначала
выжидает [окно дедупликации](concepts/reactive-cascade.md#окно-дедупликации) —
и пока он ждёт, в отчёте его не видно: все узлы в `Serving`, мейлбоксы пусты.
Поэтому граф, который выглядит успокоившимся, может ещё держать re-init в
очереди. Они не теряются — `LogTrigger` / `LogDependencyChanged` за каждым из
них сначала пишется в лог, а `close()` отбрасывает только запланированные
таймеры, — но применяются они при **следующем старте**, а не до конца текущего.

Если нужно применить их сейчас (тест, деплой, ожидающий свежее состояние на
выходе), дайте графу успокоиться перед `close()`: перестаньте слать триггеры,
подождите **дольше `dedupWindow`** после последнего, а затем дождитесь, пока
сработавшие re-init закончатся, — ни у одного узла нет `replacement` или
`stale`, а у каждого переинициализированного новый Sid (`introspect()` или
`onSidPromotion`). Неудавшийся reinit оставляет `stale=true`, пока его повтор не
пройдёт. Каскад идёт по одному уровню
зависимостей за шаг, и каждый шаг выжидает своё окно плюс re-init, поэтому для
цепочки повторяйте, пока Sid не перестанут меняться дольше `dedupWindow`.

#### Сколько нужно heap и можно ли ограничить число одновременных init?

Рассчитывайте heap на **полезную нагрузку свойств** (ячейки `byte[]`, которые
возвращает `init`), а не только на живые объекты, — и на **несколько её копий**:
движок и бэкенд лога копируют нагрузку по пути в лог и ещё раз по пути обратно.
Замер на `FileLogBackend` с нагрузкой 50 МБ, разложенной по 8 ячейкам:

- **холодный старт** в пике занял примерно **6,5–7 × нагрузку**. Пока
  записывается результат `init` одного узла, в heap одновременно лежат: map,
  которую вернул `init`; запись движка `LogInitialized` (её конструктор
  глубоко копирует каждую ячейку); копия с проставленными часами, которую
  бэкенд на самом деле дописывает (ещё одна глубокая копия); сериализованная
  запись (`ByteArrayOutputStream`, растущий удвоением, и затем его копия из
  `toByteArray()`); для записи больше 1 МБ — **проверка чтением**, которая
  десериализует её заново, чтобы убедиться, что её можно прочитать после
  рестарта (а декодирование `LogInitialized` ещё раз глубоко копирует ячейки);
  и буфер кадра (длина, CRC, нагрузка), который пишется в файл. Независимые
  узлы инициализируются одновременно, поэтому эти пики складываются по всем
  узлам, которые инициализируются в этот момент;
- **тёплому старту** понадобилось **больше 3 × нагрузку**. Открытие
  `FileLogBackend` читает и декодирует **каждую** запись один раз, чтобы
  проверить файл (CRC, часы, декодируемость); затем стартовое сканирование
  движка читает лог ещё раз и держит последний `LogInitialized` каждого
  процесса, который загружается тёпло, — именно его получает `load`. Каждое
  декодирование выделяет сырой кадр, декодированные массивы и глубокую копию,
  которую делает конструктор записи, — плюс то, что из ячеек строит ваш `load`.

Устаревшие записи стоят времени, а не кучи: оба прохода декодируют **по одной
записи** и отпускают её перед следующей, а стартовое сканирование держит только
последний `LogInitialized` на каждое имя процесса. Поэтому тёплому старту,
`engine.snapshot()` и офлайн-[`fom-log compact`](guides/cli.md) нужна куча на
**живое состояние** (состояние, выведенное из строя записью `LogDead`, отбрасывается, как только скан до неё доходит)
и на копии **самой большой отдельной записи**, которая сейчас декодируется, — а
не на весь несжатый лог. На `PostgresLogBackend` сканирование читает окна не
больше 1 000 событий и 8 МиБ payload (одна строка крупнее — отдельно), так что
добавьте до стольких декодированных данных. Лог намного больше кучи всё равно
откроется — просто дольше, чем только что
[снятый снапшотом](concepts/snapshots.md).

Это замеры одной конфигурации, а не гарантии. Чтобы снизить пики,
**разбивайте большое состояние на несколько ячеек**, а не держите один огромный
`byte[]`, — тогда каждая копия — это набор массивов поменьше, которые сборщику
куда проще разместить, чем один гигантский непрерывный, — и, где позволяет
предметная область, на **несколько узлов**, чтобы каждая запись (и набор копий
каждого узла) оставалась меньше и ни одна не приближалась к лимиту полезной
нагрузки лога. Затем **измерьте** свой холодный и тёплый старт (например,
`-Xlog:gc` или профилировщиком heap), прежде чем фиксировать `-Xmx`.

**Reinit держит две версии.** Со стратегией по умолчанию `KEEP_OLD` старая
версия обслуживает, пока строится новая, поэтому пик во время reinit — это
старое живое состояние **плюс** новое **плюс** рабочий набор init (и копии
записей выше), пока вычисления старой версии не закончатся и не отработает её
`cleanUp`. Триггер, пришедший в это время, может запустить следующий reinit,
пока старая версия ещё дорабатывает, поэтому ненадолго версий может быть три
([подробнее](concepts/process-lifecycle.md#переинициализация)). Для узла, который не помещается в память дважды, выберите
`RELEASE_FIRST` — на весь движок через `EngineConfig.withReinitStrategy(...)` или
только для этого узла через `GraphBuilder.reinitStrategy(ReinitStrategy.RELEASE_FIRST)`
сразу после его `add(...)` (Kotlin: `process(..., reinitStrategy = ...)`). Она
сначала выводит старую версию, но тогда запросы ждут во время reinit, а неудача
оставляет узел `Dead`. Настройка узла не входит в его определение: её смена
ничего не перезапускает.

Все эти копии лежат в **heap**. Прямая (нативная) память от размера записи
не зависит: `FileLogBackend` читает и пишет кадр ограниченными кусками по
256 КиБ, поэтому временные direct-буферы JDK на каждом потоке остаются
маленькими при любом размере записи, и значения `-XX:MaxDirectMemorySize` по
умолчанию достаточно.

`OutOfMemoryError`, брошенный внутри `init` (или пока движок записывает его
результат), считается **неудачной попыткой** и повторяется с backoff в
пределах бюджета init — движок не падает, но повтор, которому нужна та же
память, падает так же, пока узел не уйдёт в `Dead`. Во время reinit при
`KEEP_OLD` тот же бюджет кончается, никого не убивая: старая версия продолжает
обслуживать, а reinit повторяется через `reinitRetryBackoffMin` — OOM считается
временным сбоем, так что повтор пройдёт, когда память освободится.

**Настройки**, ограничивающей число одновременно инициализирующихся
независимых узлов, **нет**: стартует сразу каждый узел, чьи зависимости
готовы. Если ваши init жадны до памяти или соединений, ограничьте их сами
семафором, общим для ваших инициализаторов:

```java
static final Semaphore HEAVY_INITS = new Semaphore(4);   // не больше 4 одновременно

@Override
public CompletionStage<Map<String, byte[]>> init(QueryableContext ctx) {
    try {
        HEAVY_INITS.acquire();
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new InitializationException("interrupted waiting for an init slot", e);
    }
    try {
        return CompletableFuture.completedFuture(Map.of("model", buildModel()));
    } finally {
        HEAVY_INITS.release();
    }
}
```

`init` выполняется в собственном виртуальном потоке, так что блокироваться там
можно, — но время ожидания разрешения входит в `initTimeout`: оставьте
в бюджете запас на очередь.

#### Можно ли передать работу новому экземпляру на том же хосте (blue-green)?

Не так, чтобы оба работали на одном файловом логе. `FileLogBackend` берёт
файловую блокировку ОС в конструкторе; пока её держит старый экземпляр,
`new FileLogBackend(path)` в новом **сразу** падает с
`IllegalStateException` («Cannot acquire leader lock on … — another process
holds it»). Опции «ждать блокировку» нет. Остановите старый экземпляр (его
`engine.close()` и `backend.close()` или завершение процесса освобождают
блокировку), затем запустите новый — если они перекрываются, повторяйте
конструктор:

```java
FileLogBackend backend = null;
long deadline = System.nanoTime() + Duration.ofSeconds(60).toNanos();
while (backend == null) {
    try {
        backend = new FileLogBackend(path);
    } catch (IllegalStateException lockHeld) {   // старый экземпляр ещё держит лог
        if (System.nanoTime() > deadline) throw lockHeld;
        Thread.sleep(500);
    }
}
```

Для настоящего перекрытия (резервный экземпляр перехватывает работу)
используйте `PostgresLogBackend` — см. [Несколько узлов](guides/multi-node.md).

#### Я поменял `EngineConfig` — что будет со старыми запусками?

`EngineConfig` **никогда не сохраняется**: лог хранит графы, состояния и
триггеры, а не таймауты, backoff или настройки дедупа. С каким конфигом движок
создан, с тем он и делает всё дальше — включая тёплые загрузки после рестарта и
записанные триггеры, воспроизводимые при старте. Триггер, записанный при
бюджете init 30 с и воспроизведённый после того, как вы снизили его до 5 с,
выполняется с 5 с.

#### Могут ли фабрики захватывать объекты (DI-контейнер, источник данных)?

Да. Фабрики — обычные `Supplier`: они вызываются только в той JVM, которая
установила граф, и никогда не пишутся в лог — `LogChangeGraph` хранит лишь имя,
зависимости и `param` каждого узла. После рестарта приложение снова строит и
устанавливает граф из кода. См. [Внедрение зависимостей](guides/dependency-injection.md).

#### Какой сериализатор использовать?

`FurySerDe` (из `fom-fury`) для всего реального — компактный, быстрый,
дружественный к эволюции схемы. `JavaSerializableSerDe` годится для тестов и
быстрого старта. Для недоверенного хранилища лога усильте сериализатор — см.
[Безопасность](security.md).

#### Будет ли лог расти бесконечно?

Нет, если включить [снапшоты](concepts/snapshots.md): снапшот компактизирует лог
до текущего живого состояния и архивирует остальное. Используйте
`SnapshotPolicy.FixedInterval`, `SizeBasedSnapshotPolicy`, `CompositeSnapshotPolicy` или
свою. А вот **архивы** растут: по умолчанию ни одна политика их не удаляет.
Задайте политике `keepHistory` (в HOCON — `log.rotate.keep-history`) или вызывайте
`engine.purgeArchives(n)` сами — см.
[Хранение архивов](concepts/snapshots.md#archive-retention).

#### Как менять граф без простоя?

Снова вызовите `engine.newGraph(newGraph)` — движок сравнит его с текущим графом и
применит только разницу. Чтобы изменить установленный граф (добавить или убрать
узел), используйте `engine.updateGraph(current -> …)`: он выполняет
read-modify-write атомарно. См.
[Замену графа на лету](concepts/graph-swap.md#read-modify-write-updategraph).

#### Как убедиться, что тёплый рестарт действительно пропустил `init`?

Подключите [`EngineObserver`](guides/observability.md) и проверьте, что для
каждого узла приходят `onLoad*`, но не `onInitStarted` — см.
[Идемпотентный рестарт](concepts/idempotent-restart.md).

#### `fom-core` действительно без зависимостей?

Во время выполнения он зависит только от `slf4j-api`. Всё остальное —
сериализаторы, DI, метрики, трассировка, Postgres, Kotlin DSL — отдельные
опциональные модули.

#### Какой JDK нужен?

JDK 21+ во время выполнения (виртуальные потоки, pattern matching). Сборка нацелена
на toolchain JDK 21.

#### Работает ли fom под `SecurityManager`?

Нет. fom выполняет `init`, `load`, `compute`, проверки watcher'ов и свои
диспетчеры на виртуальных потоках, а в JDK 21 у виртуального потока при
установленном `SecurityManager` **нет никаких прав**, так что любая проверка
прав на этих путях падает. `SecurityManager` объявлен устаревшим к удалению, а
начиная с JDK 24 его вообще нельзя включить. Изолируйте недоверенный код
процессами или контейнерами.

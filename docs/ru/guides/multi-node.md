# Несколько узлов и лидерство

FOM — single-writer: в любой момент один **лидер** добавляет в лог; остальные
экземпляры — фолловеры. Запуск более одного экземпляра против одного лога требует
бэкенда, арбитрирующего лидерство между процессами — это `PostgresLogBackend`.

## Модель лидерства

- Последнее событие `LogLeader` называет текущего лидера. Только этот `instanceId`
  может `append`/`compact`; записи устаревшего лидера возвращают
  `Optional.empty()`. `PostgresLogBackend` проверяет это внутри транзакции
  append, поэтому отстранённый экземпляр узнаёт о перехвате на своём следующем
  `append`, а не только после перезапуска. См. [Лог](../concepts/the-log.md#лидерство-один-писатель).
- Поверх правила лога бэкенд не даёт двум экземплярам *обоим* считать себя
  лидером:
    - `FileLogBackend` — эксклюзивная ОС-блокировка файла `.lock` рядом с
      настоящим файлом лога, симлинки разрешаются (только одна машина).
    - `PostgresLogBackend` — **advisory-lock** Postgres по имени схемы и
      таблицы, удерживаемый на выделенном соединении до `close()`.

## Настройка Postgres

```java
import io.fom.jdbc.PostgresLogBackend;
import java.sql.SQLException;

// На каждом узле, указывая на ту же БД + logId.
// dataSource должен быть пулом соединений (например, HikariCP).
void serve(DataSource dataSource, Graph graph) throws SQLException {
    try (var backend = new PostgresLogBackend(dataSource, "weather");
         var engine  = new Engine(EngineConfig.defaults(), backend, new FurySerDe())) {
        engine.newGraph(graph);
        // … обслуживать до остановки …
    }   // закрывает движок, затем бэкенд — освобождая advisory-lock
}
```

Оба конструктора `PostgresLogBackend` объявляют **`throws SQLException`** (они
сразу подключаются, создают таблицу и берут блокировку), поэтому каждый пример на
этой странице либо объявляет это исключение, либо ловит его.

!!! warning "`Engine.close()` не закрывает бэкенд"
    `LogBackend` принадлежит вызывающему. Закрытие движка оставляет бэкенд — и его
    advisory-lock — удерживаемым, пока вы не вызовете `backend.close()` (или пока не
    умрёт JVM / её соединение). Для корректного failover закрывайте бэкенд явно
    после движка, как в try-with-resources выше.

- **Первый** узел, сконструировавший бэкенд, берёт advisory-lock и становится
  лидером; восстанавливает состояние и обслуживает.
- **Второй** узел, конструирующий `PostgresLogBackend(dataSource, "weather")`,
  быстро падает с `IllegalStateException` («advisory lock») — лидером он не стал.
  Поймайте это и либо повторите позже, либо работайте как standby, конструирующий
  бэкенд только после выхода лидера. Блокировка берётся до создания таблицы,
  поэтому это верно и для узлов, стартующих одновременно на совершенно новом логе.
- Конструктор также быстро падает с `IllegalStateException` на конфигурации, где
  блокировка работать не может, — см. предупреждение ниже. В этих сообщениях
  сказано, что не так (а не «advisory lock … another instance holds it»); цикл
  standby, ловящий `IllegalStateException`, должен логировать сообщение: повтор
  не исправит ошибку конфигурации.

!!! warning "Подключайтесь к writable primary — напрямую или через *сессионный* пул"
    Лидерство — это advisory-lock **уровня сессии**, поэтому каждая транзакция
    лидера должна выполняться в той серверной сессии, которая взяла блокировку.

    - **Пулинг транзакций/операторов не поддерживается.** За PgBouncer (или
      похожим прокси) в `pool_mode=transaction` или `statement` блокировка
      сессии остаётся на той серверной сессии, что её взяла, и вместе с ней
      отдаётся другим клиентам: при повторно входимом `pg_try_advisory_lock`
      лидером стал бы каждый узел. Конструктор распознаёт это, где может, и
      отказывает с `IllegalStateException` (в сообщении есть `pool_mode=session`):
      когда выданная серверная сессия уже держит блокировку этого лога, когда две
      последовательные транзакции выполняются в разных серверных сессиях
      (`pg_backend_pid()` меняется) или когда блокировка не видна из следующей
      транзакции. На тихом пуле, который каждый раз возвращает ту же серверную
      сессию, проверка этого не различит, так что не полагайтесь на неё —
      направляйте `DataSource` прямо в Postgres или в пул с `pool_mode=session`.
      (Блокировка, оставшаяся так на серверном соединении прокси, живёт, пока
      прокси не пересоздаст это соединение.) Пулы внутри JVM (HikariCP и т. п.)
      — сессионные, с ними всё в порядке.
    - **Read-only-серверы отклоняются.** На hot standby (`pg_is_in_recovery()`)
      или read-only-сессии (`default_transaction_read_only = on`) конструктор
      падает с `IllegalStateException: … the database is a read-only server (hot
      standby?) …` ещё до взятия блокировки — прежние версии брали блокировку на
      существующем логе и падали только на первой записи. Если в JDBC URL
      несколько хостов, используйте `targetServerType=primary`.
    - **Подойдёт любой уровень изоляции по умолчанию.** Пул, роль или база могут
      по умолчанию давать `REPEATABLE READ`/`SERIALIZABLE`; свои транзакции
      записи бэкенд всё равно выполняет на `READ COMMITTED`, на что опирается
      отсечение смещённого лидера (см. [Бэкенды хранения](persistence-backends.md)).

```java
void serveIfLeader(DataSource dataSource, Graph graph) throws SQLException {
    PostgresLogBackend backend;
    try {
        backend = new PostgresLogBackend(dataSource, "weather");
    } catch (IllegalStateException leaderHeldElsewhere) {
        // лидер — другой узел; отступите и повторите, или встаньте в standby.
        return;
    }
    try (backend; var engine = new Engine(EngineConfig.defaults(), backend, new FurySerDe())) {
        engine.newGraph(graph);
        // …
    }
}
```

## Failover

Когда лидер закрывает свой бэкенд, его процесс выходит или соединение рвётся,
Postgres освобождает advisory-lock. (Закрыть только движок недостаточно — см.
выше.) Standby, тогда конструирующий бэкенд, берёт блокировку, становится
лидером, восстанавливается из лога и продолжает — [идемпотентный
рестарт](../concepts/idempotent-restart.md) на другом узле.

!!! warning "Отстранённый лидер может продолжать отвечать на запросы"
    Если сессия старого лидера теряет advisory-lock, а процесс не завершается
    (backend Postgres убит, idle timeout, failover), его `engine.introspect()`
    сообщает `isLeader() == false` сразу после отстранения:
    `PostgresLogBackend.introspect()` перепроверяет блокировку (на отдельном
    соединении, никогда — на лидерской сессии). Его записи
    падают, но он может продолжать отвечать на запросы из состояния в памяти:
    `engine.query(...)` по-прежнему отвечает, а `engine.trigger(...)` синхронно
    бросает `LeadershipLostException` (наследник `IllegalStateException`,
    «… no longer holds the advisory lock … leader session was lost»), потому что
    сначала должен записать `LogTrigger`.
    Направляйте трафик (и health-check'и) по `isLeader`. Бэкенд «трогает»
    простаивающую лидерскую сессию каждые 15 с (и заодно проверяет блокировку),
    поэтому таймауты простоя длиннее этого её не завершают, а потеря блокировки
    видна примерно в пределах 15 с; `idle_session_timeout` или обрыв простоя на
    прокси **меньше 15 с** по-прежнему отстраняют узел.

    **Достоверно** потерянная блокировка отстраняет лидера сразу: лидерское
    соединение закрыто или прервано сервером (SQLState `08xxx`/`57Pxx`) либо
    проверка показала, что блокировка не удерживается. Сбой самой проверки
    (отменённый запрос — например, при шквале `pg_cancel_backend`) повторяется, а
    затем перепроверяется через отдельное соединение из `DataSource` по pid
    лидерской сессии, не дольше 3 с. Если не удалось и это, результат
    неопределённый и сразу узел не отстраняет; но если проверки остаются
    неопределёнными дольше 30 с (без единого достоверного «удерживается»),
    блокировка считается потерянной и узел отстраняется — на простаивающем узле,
    который проверяет только keepalive раз в 15 с, примерно через 45–50 с.
    Поэтому `DataSource` должен уметь выдать одно дополнительное короткоживущее
    соединение. Неопределённая проверка никогда не пропускает запись: запись
    применяется только после успешной проверки блокировки внутри её собственной
    транзакции.

    **`socketTimeout` — это ещё и ручка отстранения.** Если база «замирает»
    дольше заданного `socketTimeout`, pgjdbc завершает запрос ошибкой уровня
    соединения (SQLState `08xxx`), а бэкенд читает это как «лидерская сессия
    потеряна» и отстраняет узел **навсегда** — даже если база вернулась и сессия
    всё ещё держит блокировку. Произойдёт ли это при конкретной паузе — вопрос
    таймингов: отстранение случается, только если запрос на лидерской сессии
    (запись или проверка блокировки из keepalive раз в 15 с) провисит внутри
    паузы достаточно долго, чтобы упереться в `socketTimeout`. Чтения и
    `introspect()` ничего не посылают по лидерской сессии, поэтому никакое
    количество health-check'ов во время паузы не может отстранить узел. Поэтому
    одна и та же заморозка может отстранить один узел и быть пережитой другим. Ставьте
    `socketTimeout` выше самой долгой паузы, которую хотите пережить (и ниже
    времени, которое готовы висеть), и заведомо выше интервала keepalive в 15 с.

    **Закрывайте отстранённый бэкенд.** Отстранение останавливает записи, но не
    завершает сессию: узел, отстранённый потому, что блокировку не удалось
    подтвердить, может всё ещё её держать, и standby будет получать отказ, пока
    отстранённый узел не вызовет `backend.close()` (или пока его соединение не
    умрёт). Отстранённый бэкенд нужно закрыть, чтобы standby смог перехватить
    лидерство. Закрытый бэкенд продолжает отвечать на `introspect()` — последней
    известной ему длиной (её поддерживают его чтения и append'ы) и счётчиками
    событий последнего `introspect()`, без лидера, так что
    `EngineReport.isLeader()` равен `false` — тогда как `append`, `compact`, `get`
    и `length` по-прежнему падают с `IllegalStateException`. Поэтому эндпойнт
    `/health`, построенный на `engine.introspect()`, после закрытия бэкенда
    продолжает сообщать «не лидер», а не начинает бросать исключение. Закрытие
    движка после этого пишет **по одному `WARN` на процесс**: очистка каждого
    процесса добавляет в лог информационное событие `LogCleanedUp`, которое на
    закрытом бэкенде не записывается, о чём и сообщает предупреждение. Ждите
    этой серии WARN'ов на остановке всякий раз, когда бэкенд закрывается первым, —
    ничего не теряется, каждый процесс всё равно доходит до `Dead`, а
    `engine.close()` завершается нормально. Между двумя закрытиями движок шумит
    ещё сильнее, потому что `IllegalStateException` закрытого бэкенда считается
    временной ошибкой. `trigger()` бросает `IllegalStateException`, но reinit
    всё равно может начаться (реактивный каскад, автоматический повтор):

    - При `KEEP_OLD` (по умолчанию) процесс всё это время отвечает текущей
      версией из памяти. Каждая попытка init выполняет ваш `init` целиком и не
      может сохранить результат: `ERROR` «could not persist LogInitialized for
      init attempt &lt;n&gt;» и `WARN` «init attempt &lt;n&gt; failed», с
      обычным backoff init, пока не исчерпан бюджет init. Тогда reinit
      сдаётся (`WARN` «re-init gave up; keeps serving &lt;sid&gt;: …») и
      повторяется через `reinitRetryBackoffMin` — и так до `engine.close()`.

    При `RELEASE_FIRST`:

    - Reinit, **запрошенный** в это время (или ещё не записавший свой `LogDead`),
      пишет `ERROR` «could not persist LogDead for &lt;sid&gt; (attempt
      &lt;n&gt;); retrying reinit in &lt;ms&gt; ms» и повторяет попытки с backoff
      (`ERROR` на попытках 1, 2, 4, 8, …) до `engine.close()`. Процесс продолжает
      отвечать текущим состоянием из памяти, а `trigger()` бросает
      `IllegalStateException`.
    - Reinit, уже **прошедший свой `LogDead`** — очищающий старое состояние или
      находящийся внутри `init`, — отдавать больше нечего. Его очистка пишет `WARN`
      «could not persist LogCleanedUp», затем каждая попытка init полностью
      выполняет ваш `init` и не может сохранить результат: `ERROR` «could not
      persist LogInitialized for init attempt &lt;n&gt;» плюс `WARN` «init attempt
      &lt;n&gt; failed», с обычным backoff init. Процесс остаётся в `Initializing`
      без Sid, пока не кончится бюджет init (`EngineConfig.initTimeout`,
      суммарно на все попытки), затем пишет `ERROR` «giving up: Init for
      &lt;name&gt; ran out of its … budget» и переходит в `Dead`. Запросы к нему
      всё это время ждут — поэтому уходят в таймаут запроса, а те, что ещё ждут в
      момент перехода в `Dead`, падают с `QueryRejectedException` («&lt;name&gt;
      is Dead»), как и все последующие. Процесс в фазе load заканчивает так же
      (`ERROR` «could not persist LogLoaded …», повторы load, откат к init).

    Где возможно, закрывайте сначала движок, а сразу за ним бэкенд.

!!! note "Отстранение посреди reinit"
    Reinit, чью запись отклонили из-за того, что узел потерял лог (запись
    `LogInitialized` или `LogLoaded` отклонена или бросает
    `LeadershipLostException`), сразу сдаётся. При `KEEP_OLD` старая версия
    продолжает обслуживать запросы, узел помечается устаревшим, движок пишет
    `ERROR` «lost leadership during init» (или «load») и `WARN` «re-init gave
    up; keeps serving &lt;sid&gt;: …» и вызывает `EngineObserver.onReinitFailed`
    с `LeadershipLostException`. Повтора нет: лидерство не возвращается.
    О потере сообщается один раз на обслуживающий Sid: следующий запрос reinit
    для этого процесса (например, от каскада) молча отбрасывается — без запуска
    `init` и без нового колбэка, — и узел остаётся устаревшим. Уже записанная
    новая версия остаётся в логе; следующий лидер загрузит её при старте (лидер,
    у которого узел работает с `RELEASE_FIRST`, вместо этого снимет её и
    выполнит холодный init). При `RELEASE_FIRST` reinit, чей `LogDead` отклонён, отбрасывается, и
    процесс продолжает обслуживать то состояние, что у него есть; reinit, уже
    прошедший свой `LogDead`, обслуживать больше нечем, и процесс заканчивается
    в `Dead` ([Жизненный цикл процесса](../concepts/process-lifecycle.md#переинициализация)).

!!! note "`close()` действительно освобождает блокировку"
    `close()` снимает блокировку явно, при неудаче повторяет попытку с короткой
    паузой и проверяет в той же сессии, что блокировки больше нет. Если это не
    удаётся (например, каждый запрос отменяется), он пишет `WARN` и прерывает
    соединение (`Connection.abort`), а не возвращает его в пул, так что
    физическая сессия пула — и её блокировка — завершается, и standby может
    перехватить лидерство. Задайте в `DataSource` таймаут соединения и таймаут
    сокета (pgjdbc: `connectTimeout`, `socketTimeout`): без них чтения висят,
    пока Postgres не отвечает, — но, выбирая маленький `socketTimeout`,
    учитывайте описанный выше компромисс с отстранением. `introspect()` сам ограничивает свою работу с
    базой 5 с и после этого сообщает последние известные значения.

!!! note "Восстановление — работа лидера"
    Снапшоты/компактизация и установка графа — только для лидера. Фолловер,
    ставший лидером, воспроизводит лог для пересборки состояния; процессы тёпло
    загружают свой последний живой `LogInitialized`.

## Отказ базы данных

Advisory-lock координирует *узлы*; для *базы* он ничего не делает. Лог ровно
настолько долговечен, насколько долговечна ваша конфигурация Postgres:

- При **асинхронной** потоковой репликации переключение на реплику теряет
  транзакции, которые старый primary уже подтвердил, но ещё не отправил. Для fom
  это значит, что дописанные события — `LogInitialized`, триггеры, захваты
  лидерства, — по которым движок уже действовал (и отвечал на запросы), из лога
  просто исчезают. Новый лидер восстанавливается по укороченному логу и заново
  выдаёт потерянные clock'и и `Sid` новым событиям — ровно как после
  восстановления из бэкапа (см. [Sid и clock](../concepts/sid-and-clock.md)).
  Используйте **синхронную** репликацию (`synchronous_commit = on` /
  `remote_apply` вместе с `synchronous_standby_names`), если подтверждённые
  события должны переживать failover.
- `Engine` и его `PostgresLogBackend` **не умеют переключаться между хостами**.
  Бэкенд держит одну лидерскую сессию всю свою жизнь (на ней живёт
  advisory-lock); когда primary пропадает, эта сессия умирает, бэкенд
  отстраняет себя (`isLeader() == false`, записи падают с
  `LeadershipLostException`) и остаётся отстранённым — он не переподключается.
  После отказа базы **закройте движок и бэкенд** и откройте новые на новом
  primary: новый бэкенд возьмёт блокировку на новом сервере, а движок
  восстановится там из лога.
- Направляйте `DataSource` на роль primary, а не на хост: multi-host URL с
  `targetServerType=primary`
  (`jdbc:postgresql://db1,db2/app?targetServerType=primary`) или виртуальный IP /
  DNS-имя, следующее за primary. Тогда *новый* бэкенд (и переподключения пула)
  попадут на новый primary без изменения конфигурации. Бэкенд, открываемый на
  сервере только для чтения, отклоняется (см.
  [Бэкенды хранения](persistence-backends.md#postgreslogbackend)).

## Выбор бэкенда

| У вас… | Используйте |
|---|---|
| один процесс, эфемерное состояние | `InMemoryLogBackend` |
| один процесс, долговечное состояние | `FileLogBackend` |
| несколько процессов/узлов, HA | `PostgresLogBackend` |

Ключ advisory-lock — 64-битный хеш схемы (`current_schema()`, где лежит
таблица) и имени таблицы, поэтому разные таблицы не коллизируют по блокировке —
в том числе один и тот же `logId` в двух схемах (`sa.fom_log_x` и `sb.fom_log_x`
— два лога, у каждого свой лидер). Прежние версии хешировали только имя таблицы
и отказывали лидеру второй схемы с «another instance holds it». Поэтому ключ
изменился: не запускайте узлы старой и новой версии на одном логе одновременно
(они не увидят блокировку друг друга) — остановите старые, прежде чем
запускать новые (см. также [Обновления](../concepts/idempotent-restart.md#upgrades)).
Если они всё же пересеклись, барьер записи не даст узлу новой версии дописывать
после захвата лога старым узлом, но узел старой версии так себя не ограждает.

!!! warning "Ключи блокировок и производные имена снова изменились"
    Ключ блокировки теперь — первые 8 байт **SHA-256** от `schema.table`; раньше
    это был полиномиальный хеш строки (`h = 31·h + c`), на котором разные
    короткие имена совпадают — `public.fom_log_ar0` и `public.fom_log_c2n` делили
    одну блокировку, и лидером мог стать только один из двух логов. Тот же
    слабый хеш сокращал длинные производные имена (таблицы архивов,
    последовательности `row_id`, первичные ключи), так что два длинных id логов
    могли получить одинаковые имена. Теперь оба используют хеш на SHA-256. Что
    это меняет при обновлении:

    - **Остановите все узлы старой версии до запуска новой**: старые и новые
      узлы берут на одном логе разные блокировки и оба стали бы лидерами (барьер
      записи ограничивает ущерб, как описано выше, но не делает это безопасным).
    - Таблицы с именем длиннее 55 байт (суффикс последовательности/первичного
      ключа уже не влезает) сохраняют существующие последовательность и индекс —
      они берутся из каталога, — но новые таблицы и новые архивы получают новые
      имена.
    - Архивы теперь ещё и помечаются комментарием таблицы
      (`fom archive of <table>`), и `purgeArchives` удаляет только помеченные.
      Архивы, записанные прежними версиями, **больше не удаляются**; удалите их
      вручную или пометьте — пометка работает только для коротких имён таблиц
      (примерно до 40 байт); архивы длинных, сокращённых имён несут старый хеш и
      не находятся даже с пометкой, так что их удаляйте вручную (см.
      [Бэкенды хранения](persistence-backends.md#postgreslogbackend)). Имя таблицы по умолчанию — `fom_log_<logId>`, и
конструктор с двумя аргументами **отклоняет** `logId` с символами, отличными от
ASCII-букв, цифр и `_` (`IllegalArgumentException`), — прежние версии заменяли их
на `_`, и `weather-eu` и `weather_eu` молча делили одну таблицу и блокировку. Если
нужно другое имя, передайте его явно в конструктор с тремя аргументами.
Имена таблиц не различают регистр, как и любые идентификаторы Postgres без
кавычек: `Weather` и `weather` — один и тот же лог с одной блокировкой (второй лидер
будет отклонён). Имена, содержащие `_archived_` (зарезервировано для архивов),
зарезервированные слова SQL и имена, уже занятые объектом, который не является
таблицей (представление, последовательность, …), отклоняются с
`IllegalArgumentException`; так же отклоняются существующая таблица, которая не
является таблицей лога (нет `row_id`, …), имя, которое `search_path` разрешает
вне текущей схемы (например, `pg_class`), и новый лог, имя последовательности
или первичного ключа которого уже занято таблицей другого лога (лог `cz` рядом с
логом `cz_rid_seq`) — см.
[Бэкенды хранения](persistence-backends.md#postgreslogbackend). Если в базе задан
`statement_timeout`, логи из больших событий остаются читаемыми при failover:
чтение диапазона забирает не более 8 МиБ payload за один запрос.

## Замечание о безопасности

Любой, кто может писать в таблицу лога Postgres, может подложить байты, которые
лидер прочитает. Десериализация бэкенда фильтруется allowlist'ом, но всё равно
ограничьте привилегии таблицы. См. [Безопасность](../security.md).

# CLI `fom-log`

`fom-log` — автономный инструмент командной строки для инспекции, диагностики и
компакции файлов `FileLogBackend`. Удобен для офлайн-отладки и сжатия
продакшен-лога.

## Команды

```text
fom-log inspect  <path>   # сводка + первый/последний clock + счётчики событий по типам
fom-log events   <path>   # по строке на событие: позиция, clock, тип, ключевые поля
fom-log diagnose <path>   # проверка CRC по фреймам; отчёт о повреждении
fom-log compact  <path>   # офлайн-снапшот: оставить живое состояние, остальное в архив
fom-log help     <command> # справка по команде (то же, что fom-log <command> --help)
```

Каждая команда понимает `-h`/`--help` и `-V`/`--version`. Коды завершения: `0` —
успех, `1` — лог повреждён или заканчивается неполным фреймом, `2` — путь не
существует или недоступен для чтения либо задана неверная опция. Несуществующий
путь выводится как `No such file: <путь>`; путь, который утилита не может даже
проверить (обычно потому, что у вашего пользователя нет права на поиск в одном из
родительских каталогов), — как `Cannot access <путь> (permission denied?)`.

### inspect

Печатает id лога, длину, текущего лидера, clock первого и последнего события
(у последнего — наибольший clock), наибольшую метку времени события (максимум по
всем событиям — не обязательно у последнего: настенные часы могут отступить назад,
а компакция сохраняет старые метки) и счётчик событий по типам. После компакции в логе есть не все clock'и между первым и последним —
тогда `inspect` сообщает, сколько их не хватает:

```text
$ fom-log inspect /var/lib/fom/weather.bin
Log: /var/lib/fom/weather.bin
Length: 128 event(s)
Current leader: fom-7f3c…
First clock: 0 (position 0)
Last clock: 12967 (position 127)
Clock gaps: 12840 clock(s) between first and last are absent (compacted away)
Highest event timestamp: 1737045123456
Counts by type:
  LogLeader                 3
  LogInitialized           40
  …
```

### events

Выводит события по одному на строку: **позицию** (индекс в файле), **clock**,
время, тип и поля, важные для этого типа. В логе, который ни разу не
компактизировался, позиция и clock совпадают, а после компакции расходятся —
`Sid` из `Engine.introspect()` (`processName@clock`) ищите по clock.

После компакции колонка `TIMESTAMP` **не** возрастает: события, сохранённые
снапшотом, оставляют свои исходные, более старые метки времени, а синтетический
`LogLeader` на clock `0` (и завершающие `LogTrigger`/`LogPaused`/`LogSnapshot`)
несут время стенных часов момента компакции — так что первая строка запросто
может оказаться свежее строк под ней. Вывод упорядочен по позиции и clock'у, как
и сам лог; метки времени — метаданные события, а не ключ сортировки. См.
[Снапшоты и компакция](../concepts/snapshots.md#что-содержит-снапшот).

```text
fom-log events <path> [--from POSITION] [--limit N] [--type TYPE[,TYPE…]] [--process NAME] [--full]
```

```text
$ fom-log events /var/lib/fom/weather.bin --type LogPaused,LogResumed
POSITION  CLOCK       TIMESTAMP                 TYPE                  DETAILS
41        12901       2025-01-16T16:31:10.120Z  LogPaused             process=Alerts stale=false forDependency=false (operator pause)
42        12902       2025-01-16T16:31:10.121Z  LogPaused             process=Quotes stale=true forDependency=true (paused because a dependency is paused)
57        12950       2025-01-16T16:40:02.004Z  LogResumed            process=Alerts
```

| Тип | Что показывается |
|---|---|
| `LogLeader` | `instance=` — id экземпляра-лидера |
| `LogChangeGraph` | число узлов и их имена |
| `LogInitialized` | `sid=name@clock`, `replaces=name@clock`, если init заменяет ещё обслуживающую версию, ключи свойств — до 10 целиком; больше — числом и первыми 10 (`properties=12345 keys [a, b, … +12335 more]`), если не задан `--full` |
| `LogLoaded`, `LogDead` | `sid=name@clock` |
| `LogCleanedUp` | `sid=name@clock`, `ok=` |
| `LogTrigger` | имена запущенных процессов |
| `LogDependencyChanged` | `sid=`, `dep=` — имя зависимости, `depClock старый -> новый` |
| `LogSnapshot` | `checkpointClock=` |
| `LogPaused` | `process=`, `stale=`, `forDependency=` — пауза оператора или пауза из-за приостановленной зависимости |
| `LogResumed` | `process=` |

- `--from POSITION` — начать просмотр с этой позиции (по умолчанию `0`).
- `--limit N` — вывести не больше `N` событий (по умолчанию `1000`). Если
  подходящих больше, в stderr печатается `NOTE` со значением `--from`, с
  которого можно продолжить.
- `--type` — только события этих типов (через запятую или повтором опции).
  Неизвестное имя типа — код `2` и список допустимых.
- `--process NAME` — только события, касающиеся процесса: его инициализация,
  загрузка, завершение, очистка, паузы и возобновления, триггеры с его именем и
  изменения зависимостей — как у него самого, так и у зависимости с именем
  `NAME`. События лидера, графа и снапшота не выводятся.
- `--full` — выводить все ключи свойств `LogInitialized` (по умолчанию для
  процесса с более чем 10 ключами выводится их число и первые 10 по алфавиту,
  чтобы большой процесс не давал строку в несколько мегабайт).

Как и `inspect`, команда читает временную копию; если лог заканчивается неполным
последним фреймом, печатает `WARNING`, выводит читаемый префикс и завершается с
кодом `1`. С логом, повреждённым **внутри** (такой движок открыть откажется),
поведение то же: `WARNING` называет байтовое смещение плохого фрейма и сколько
событий читается до него, список покрывает эти события (фильтры и `--from`
применяются к ним), код завершения — `1`. Ничего после повреждения не
выводится — причину покажет `diagnose`. По смещению обрезается только временная
копия; ваш файл не трогается.

### diagnose

Обходит все фреймы, проверяя CRC и round-trip события. Если фрейм повреждён или
неполон, сообщает его байтовое смещение и число событий, читаемых до него, и
завершается с кодом `1`. Нечитаемое событие указывается по позиции (и clock
последнего читаемого события перед ним). Несуществующий или нечитаемый путь —
код `2`.

```text
$ fom-log diagnose /var/lib/fom/weather.bin
Opened: /var/lib/fom/weather.bin (40213 bytes, read via a temporary copy)
Readable events: 128
Diagnose OK: all 128 events round-tripped.
```

**Пустой** (0 байт) файл — не повреждение: в него ещё ничего не записано, даже
заголовок, и движок считал бы его новым пустым логом. `diagnose` так и пишет и
завершается с кодом `0` (`Diagnose OK: the file is empty (0 bytes, no header
yet); an engine would treat it as a new, empty log; nothing to check.`);
`inspect` добавляет то же примечание к сводке, а `events` выводит его вместо
`No matching events`.

`diagnose` также различает два вида повреждений. **Оборванный последний фрейм** —
недописанная последняя запись, то, что оставляет падение посреди append, —
выводится так:

```text
Diagnose FAIL: log is corrupt at byte offset 40209 of 40213: 128 event(s) readable before it, ...
Cause: torn last frame — the final 4 byte(s) are an incomplete append, which is what a crash mid-append leaves behind. The next engine open cuts them off and saves them next to the log as weather.bin.truncated.<millis>; all 128 event(s) before it are intact and nothing else is damaged.
```

то есть ничего делать не нужно: движок восстановится сам. При **любом другом**
повреждении (испорченный фрейм, за которым идут ещё данные, целый фрейм, который
не декодируется, или событие, чей clock не больше предыдущего, — лог, склеенный
из двух линий времени) печатается причина из `LogCorruptedException` и строка
`This is damage inside the log, not a torn last frame: an engine refuses to open
it and leaves the file untouched.`

!!! note "`inspect`, `events` и `diagnose` никогда не изменяют ваш файл"
    Они копируют лог во временный файл и открывают копию: они
    не берут лидерскую блокировку, не обрезают оригинал на повреждённом фрейме и
    работают с логом, который держит открытым работающий движок. (Копия живого
    лога может заканчиваться недописанным фреймом — это будет отмечено как
    повреждение.) Если лог заканчивается неполным последним фреймом, `inspect`
    печатает `WARNING` в stderr, сводка покрывает только читаемый префикс, а
    команда завершается с кодом `1`. При
    любом другом повреждении — таком, что движок отказывается открыть лог с
    `LogCorruptedException` (см.
    [Бэкенды хранения](persistence-backends.md#filelogbackend)), — `inspect`
    вместо сводки печатает `WARNING` с байтовым смещением и завершается с кодом
    `1`, `events` печатает тот же `WARNING` и выводит события до этого смещения
    (код `1`), а `diagnose` печатает `Diagnose FAIL` со смещением и затем причину.
    В выводе всегда фигурирует **ваш** файл, а не временная копия — в том числе
    когда файл вообще не является логом fom и команда завершается сообщением
    `Failed to open <ваш путь>: ...` (код `2`).

!!! note "Временной копии нужно свободное место"
    Каждая из этих команд (и `compact` — для предварительной проверки) сначала
    копирует **весь** лог в новый каталог внутри `java.io.tmpdir` JVM (в Linux по
    умолчанию `/tmp`), поэтому там должно быть свободно не меньше размера лога;
    копия удаляется по завершении команды. Если копию сделать не удалось — диск
    заполнен, нет права на запись, — команда завершается кодом `2` с сообщением
    `Failed to open <ваш путь>: could not make the temporary working copy of the
    log in <временный каталог> (...)`, где назван временный каталог; ваш лог не
    изменялся. Если причина — заполненный диск или исчерпанная квота, сообщение
    называет нужное число байт и советует освободить там место; при любой другой
    причине (`Read-only file system`, `AccessDeniedException`, ...) оно говорит, что
    каталог недоступен для записи. В обоих случаях копию можно направить в другое
    место, например `JAVA_OPTS=-Djava.io.tmpdir=/var/tmp fom-log inspect ...`.

### compact

Компактизирует лог офлайн — то же, что [`Engine.snapshot()`](../concepts/snapshots.md)
делает в работающем движке. Оставляет запись о лидере, живое состояние каждого
процесса (перед каждым — граф, под которым оно записано; текущий граф последним)
и все паузы, а прежнее содержимое переносит в соседний
`<файл>.archived.<timestamp>`.

```text
$ fom-log compact /var/lib/fom/weather.bin
Compacted /var/lib/fom/weather.bin: 12840 -> 43 event(s)
Previous contents archived to /var/lib/fom/weather.bin.archived.1737045123456
```

- Запускайте, когда приложение **остановлено**. Лог, открытый работающим
  движком, отклоняется (код `2`): файловая блокировка бэкенда занята.
- **Пустой** (0 байт) файл отклоняется (код `2`) с сообщением `the file is
  empty (0 bytes); nothing to compact; it was not modified` и остаётся в
  точности как был — заголовок не пишется, файл `.lock` не создаётся.
- Любая другая ошибка — каталог, недоступный для записи, нет места на диске —
  завершается кодом `2` с сообщением `Cannot compact <ваш путь>: ...`, за которым
  следует вся цепочка причин, так что видно, что именно произошло (например,
  `java.nio.file.AccessDeniedException: /var/lib/fom/weather.bin.tmp`) и с каким
  файлом. Компакция пишет соседний `<файл>.tmp`, поэтому ей нужен доступ на
  запись в **каталог** лога, а не только в сам файл.
- **Повреждённый** лог — в том числе заканчивающийся всего лишь неполным
  последним фреймом — отклоняется (код `1`) и не изменяется, так что ничего не
  отрезается без вашего ведома. Сначала запустите `diagnose`; при повреждении,
  отличном от оборванного последнего фрейма, сделайте резервную копию файла и
  восстановите его или обрежьте до сообщённого смещения.
- После компакции приложение стартует так же, как раньше: живое состояние
  загружается тёпло, процессы на паузе остаются на паузе. Та же логика доступна в
  коде как `LogCompaction.compact(backend)`.

## Запуск

`fom-log` собирает исполняемый дистрибутив (через Gradle-плагин `application`):

```bash
./gradlew :fom-log:installDist
./fom-log/build/install/fom-log/bin/fom-log inspect /path/to/log.bin
```

!!! danger "Считайте входные файлы доверенными"
    `inspect`/`events`/`diagnose`/`compact` десериализуют полезные нагрузки лога. Файловый бэкенд
    применяет allowlist-фильтр десериализации (только `io.fom.*` + JDK-типы), а
    `diagnose` в основном проверяет CRC — но запускайте CLI только на файлах,
    которым доверяете. См. [Безопасность](../security.md).

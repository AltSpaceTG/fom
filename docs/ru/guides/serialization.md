# Сериализация

Через сериализатор движок пишет в лог ровно один вид значений пользовательских
типов: `param` каждого узла. Это работа SPI **`SerDe`**. Выбор и усиление `SerDe` —
важное для безопасности решение конфигурации; читайте эту страницу вместе с
[Безопасностью](../security.md).

## SPI `SerDe`

```java
public interface SerDe {
    byte[] serializeParam(String processName, Serializable param);
    Object loadParam(String processName, byte[] bytes);
}
```

`LogChangeGraph` записывает через него `param` каждого узла, чтобы при рестарте
понять, изменилось ли определение узла с момента сохранения состояния. Движок
читает param обратно только для этого сравнения, поэтому `SerDe` должен
восстанавливать param в значение, `equals` исходному (это проверяет
`SerDeContractTest` из `fom-test`; схемный `SerDe` подставляет свои образцы param,
переопределив `sampleParams()`, — см. [Тестирование](testing.md#свой-serde)).

Всё остальное в логе — либо типы fom, либо непрозрачные байты:

- **свойства процесса** — ячейки `Map<String, byte[]>`, которые возвращает ваш
  `init`, — хранятся как есть; кодируйте каждую ячейку через `Codec` (см.
  [Конфигурацию](configuration.md#типизированные-ячейки-свойств));
- **значения триггеров** не хранятся — `LogTrigger` записывает только, каким
  процессам запрошена переинициализация;
- **фабрики и резолверы динамических маршрутов** никогда не сериализуются — они
  живут в коде.

## Выбор реализации

### `FurySerDe`

`fom-fury` оборачивает [Apache Fury](https://fury.apache.org/): компактный,
быстрый, дружественный к эволюции схемы (добавление nullable-поля в record не
сломает читателей, собранных против старой схемы). Создавайте один экземпляр на
движок и переиспользуйте.

```java
import io.fom.fury.FurySerDe;

var serDe = new FurySerDe();                          // разрешающий (по умолчанию)
var strict = FurySerDe.strict(TenantParam.class);     // регистрация обязательна
```

- Конструктор без аргументов оставляет регистрацию классов **выключенной** — без
  настройки, но Fury инстанцирует любой класс, названный в байтах.
- `FurySerDe.strict(...)` (то же, что `new FurySerDe(true, classes)`) включает
  гейт регистрации классов Fury — его сильнейшую защиту от вредоносных байтов.
  Тогда вы контролируете, какие именно классы можно десериализовать.

В строгом режиме JDK-коллекции, строки, boxed-примитивы и `byte[]` Fury
регистрирует сам. **Зарегистрировать нужно каждый тип `param` процесса**
(`GraphBuilder.addWithParam`) и любые вложенные в него не-JDK типы — больше через
`SerDe` ничего не проходит. Регистрация выдаёт числовые id по порядку, поэтому
передавайте классы в стабильном порядке и только дописывайте новые в конец.
`new FurySerDe(true)` без классов работает, только если ни один процесс не
принимает `param` не-JDK типа.

Когда выбирать строгий режим — см. [Безопасность](../security.md).

### `JavaSerializableSerDe` (тесты, быстрый старт)

Встроенный `SerDe` `fom-core` использует `ObjectOutputStream`/`ObjectInputStream`.
Param должен реализовывать `java.io.Serializable` (это и так обязательно).

```java
import io.fom.serde.JavaSerializableSerDe;
import io.fom.serde.ObjectInputFilters;

var serDe = new JavaSerializableSerDe();                      // фильтр ограничения ресурсов
var hardened = new JavaSerializableSerDe(myObjectInputFilter); // ваш allowlist
```

Каждый `readObject()` выполняется под `ObjectInputFilter`:

- по умолчанию (`ObjectInputFilters.resourceLimits()`) ограничивает глубину,
  ссылки, байты потока и длину массива (не более 10 000 000 элементов — полезная
  нагрузка с массивом больше отклоняется), чтобы притупить «бомбы десериализации», при
  этом допуская неизвестные пользовательские классы;
- передайте свой `ObjectInputFilter` (например, строгий allowlist классов) через
  конструктор для продакшена, или задайте общесистемный `jdk.serialFilter`.

!!! danger "Java-сериализация — известный вектор RCE"
    Даже с фильтром ограничения ресурсов нефильтрованная десериализация классов из
    байтов, контролируемых атакующим, опасна. Для продакшена с недоверенными
    байтами лога предпочитайте `FurySerDe.strict(...)` или передавайте строгий
    allowlist-фильтр. См. [Безопасность](../security.md).

## Усиление полезной нагрузки лога (автоматически)

**Бэкенды лога** (`FileLogBackend`, `PostgresLogBackend`) восстанавливают
только собственные `io.fom.*` записи событий плюс JDK-типы и `byte[]` — ваши
param остаются внутри `byte[]`, пока `SerDe` не декодирует их отдельно.
Поэтому эти бэкенды применяют **строгий allowlist**-фильтр
(`ObjectInputFilters.logPayload()`) на своём внутреннем `readObject`, отклоняя
любой класс не из `io.fom`/JDK. Это встроено; настраивать не нужно.

Тот же фильтр ограничивает полезную нагрузку каждого события: не более 64 МиБ
на событие, массивы не длиннее 10 000 000 элементов (например, свойство типа
`byte[]`), не более 1 000 000 ссылок на объекты и глубина вложенности до 64
(описание лимитов возвращает `ObjectInputFilters.logPayloadLimits()`). Событие
сверх этих лимитов невозможно было бы прочитать после рестарта, поэтому оба
бэкенда отклоняют его ещё при `append` с `IllegalArgumentException`, в
сообщении которого перечислены лимиты. Если `init` возвращает свойства такого
размера, процесс сразу уходит в `Dead`, без повторов, а
`NodeReport.lastException` показывает это сообщение. Храните объёмные данные вне
лога (в файле или таблице), а в лог сохраняйте ссылку на них.

На практике первым упирается в лимит ссылок большое *число* мелких свойств.
Init сохраняется одним событием, свойства которого — map ключ → `byte[]`, и
каждое свойство стоит примерно **2 ссылки** (ключ `String` и значение `byte[]`).
Поэтому процесс, чей `init` возвращает около **500 000 свойств**, упирается в
лимит 1 000 000 ссылок, как бы мало ни было каждое из них, — задолго до потолка
в 64 МиБ. Если процесс порождает столько записей, упакуйте их в меньшее число
более крупных свойств (один закодированный `byte[]` на порцию) или, лучше,
храните их вне лога, а в лог сохраняйте только ссылку.

!!! note "CRC — это не MAC"
    Файловый бэкенд обрамляет каждое событие CRC32 для обнаружения *повреждений*.
    Это не защищённая от подделки подпись — относитесь к файлу лога как к локально
    владеемому артефакту с контролем доступа.

## Совместимость между бэкендами

Все три встроенных бэкенда внутренне сериализуют полезные нагрузки событий
Java-сериализацией, поэтому лог, записанный одним, читается другим. **Выбранный
вами `SerDe`** кодирует только param внутри `LogChangeGraph` — держите его
согласованным между рестартами одного лога.

# Мультитенантность

Частый паттерн — один процесс **на тенант** (например, `Stations_PUB1`,
`Stations_PUB2`), маршрутизируемый [`Routable`](../concepts/graph-and-routing.md)-сообщением
или динамическим маршрутом. Модуль `fom-tenant` добавляет **обёртку авторизации
defence-in-depth**, чтобы вызывающий мог трогать только разрешённые ему тенанты.

!!! info "Это обёртка, а не замена"
    `TenantAwareEngine` делегирует обычному `Engine`. Движок остаётся источником
    истины; обёртка добавляет проверку authz поверх `query` / `queryProcess` /
    `trigger` и вызовов жизненного цикла тенанта. Обёрнутый движок намеренно
    **не** раскрывается, поэтому код, у которого есть только обёртка, не может
    обойти проверки.

!!! tip "Тенанты не используются?"
    Тогда обёртка не нужна. У обычного `Engine` нет слоя авторизации: любой
    процесс доступен тому, у кого есть движок. `TenantAwareEngine` включается
    осознанно — для путей, обслуживающих вызовы от тенантов.

## Построение обёртки

```java
import io.fom.tenant.*;

var aware = TenantAwareEngine.builder(engine)
    .tenantResolver(TenantResolver.suffixAfter("_"))                  // "Stations_PUB1" → "PUB1"
    .authzPolicy((caller, tenant) -> caller.tenants().contains(tenant))
    .globalProcesses("Units", "Calendar")                             // доступны всем
    .build();
```

## Как решается доступ

Каждое обращение к процессу проходит одни и те же три шага, и на каждом обёртка
**fail-closed**:

1. **Объявлен глобальным** (`globalProcesses`) → `query`/`queryProcess` разрешены
   всем; `trigger` — только вызывающим, которых пускает `globalTriggerPolicy`
   (по умолчанию никому).
2. **Разрешается в тенант** → доступ, только если `authzPolicy` пускает
   вызывающего к этому тенанту. Политика по умолчанию запрещает всем.
3. **Всё остальное** — имя не относится ни к одному тенанту или неоднозначно →
   **отказ**.

### Резолверы не угадывают

`TenantResolver` отображает имя процесса в `TenantId` или ни во что:

- **`TenantResolver.suffixAfter("_")`** (по умолчанию) — строгий: имя должно быть
  ровно `<база>_<тенант>`, с одним разделителем и непустыми частями.
  `Stations_PUB1` → `PUB1`, а `Stations_ACME_EU`, `Units`, `_PUB1` ни во что не
  разрешаются и поэтому получают отказ (если не глобальные). Он никогда не берёт
  «часть после последнего `_`» — так процесс одного тенанта мог достаться другому.
- **`TenantResolver.registry(Map.of("Stations_ACME_EU", TenantId.of("ACME_EU")))`**
  — явная карта процесс → тенант для имён, содержащих разделитель. Карта
  **копируется** при построении, поэтому тенант (или процесс), добавленный на
  лету, через неё не резолвится: постройте новый резолвер — и новый
  `TenantAwareEngine` над тем же `Engine`, так как резолвер обёртки
  фиксирован, — или используйте `TenantResolver.of(...)` поверх собственного
  живого поиска (concurrent map, ваша таблица тенантов).
- **`TenantResolver.regex(Pattern.compile("Stations@(.+)"))`** — имя должно
  совпасть целиком; тенант — первая группа захвата.
- **`TenantResolver.of(name -> …)`** — любое своё правило. Если не уверены,
  возвращайте пусто.

Резолвер должен возвращать `Optional.empty()`, но никогда не `null`: на `null`
вызов падает с `IllegalStateException`, где указано имя процесса (для `query` /
`queryProcess` падает возвращённый stage).

### Глобальные процессы

Общие процессы, не принадлежащие тенантам (справочники, календари…), нужно
перечислить в `globalProcesses(...)`. Процесс, который не глобальный и не
принадлежит тенанту, через обёртку **недоступен** — неявного правила «всё без
тенанта публично» нет. Имя из списка глобальных считается глобальным, даже если
резолвер отнёс бы его к тенанту.

Для обычных вызывающих глобальные процессы доступны **только для запросов**.
Переинициализация общих данных каскадирует во все тенанты, поэтому
`aware.trigger(caller, "Units", …)` бросает `TenantAccessDeniedException`, если
вызывающего не пускает `globalTriggerPolicy`:

```java
var aware = TenantAwareEngine.builder(engine)
    .globalProcesses("Units", "Calendar")
    .globalTriggerPolicy(caller -> caller.identity().equals("ops"))   // по умолчанию: никому
    .build();
```

## Вызывающие и тенанты

```java
TenantId pub1 = TenantId.of("PUB1");
TenantCaller alice = TenantCaller.of("alice", pub1);     // может действовать с PUB1
TenantCaller anon  = TenantCaller.anonymous();           // нет тенантов
```

Повторяющиеся id тенантов, переданные в `TenantCaller.of` (например, из claims
токена), схлопываются.

## Авторизованные операции

Константы `ProcessRef` — это **поля**, а не выражения: объявляйте их на классе,
как это делает [Граф и маршрутизация](../concepts/graph-and-routing.md#типизированные-ссылки-на-процессы--processref),
и передавайте туда, где ожидается имя:

```java
final class Refs {
    static final ProcessRef STATIONS_PUB1 = ProcessRef.of("Stations_PUB1");
}
```

```java
// query: принимаются только Routable-сообщения (цель известна заранее)
aware.query(alice, new GetStations("PUB1"));            // ok, если у alice есть PUB1

// явная адресация
aware.queryProcess(alice, "Stations_PUB1", msg);

// триггер
aware.trigger(alice, "Stations_PUB1", new RefreshSignal("x"));

// таймаут на запрос — как Engine.query(msg, timeout) / queryProcess(name, msg, timeout)
aware.query(alice, new GetStations("PUB1"), Duration.ofMillis(200));
aware.queryProcess(alice, "Stations_PUB1", msg, Duration.ofMillis(200));

// ProcessRef вместо строкового имени
aware.queryProcess(alice, Refs.STATIONS_PUB1, msg);
aware.queryProcess(alice, Refs.STATIONS_PUB1, msg, Duration.ofMillis(200));
aware.trigger(alice, Refs.STATIONS_PUB1, new RefreshSignal("x"));

// пакетный триггер — одна долговременная запись на несколько процессов, и все они
// в собственном тенанте alice (чужое имя в любом месте карты отклоняет весь пакет,
// см. ниже)
aware.trigger(alice, Map.of(
    "Stations_PUB1", new RefreshSignal("x"),
    "Alerts_PUB1",    new RefreshSignal("y")));
```

Каждая перегрузка выполняет ту же авторизацию, что и её базовый вариант:
`ProcessRef` приводится к `name()` и проверяется до любой отправки, а отказ
завершает возвращённый stage ошибкой (`query`/`queryProcess`) или бросает
исключение (`trigger`).

### Пакетный триггер { #batch-trigger }

`trigger(TenantCaller, Map<String, Serializable>)` — это tenant-aware форма
[`Engine.trigger(Map)`](../concepts/triggers-and-watchers.md#триггеры), и она даёт
две гарантии, которых цикл по однопроцессной форме дать не может:

- **Авторизация «всё или ничего».** Сначала проверяется каждое имя из map —
  принадлежность тенанту и заданный в builder'е `globalTriggerPolicy` для
  глобального процесса. Одно чужое имя или одно глобальное имя, для которого
  `globalTriggerPolicy` этого вызывающего не принимает, роняет вызов
  `TenantAccessDeniedException`, и **ничего** не триггерится: частично
  применённого пакета не бывает.
- **Пакет — одна долговременная запись.** Цикл из однопроцессных триггеров пишет
  по одному `LogTrigger` на процесс, поэтому потерянный на середине лог может
  оставить пакет применённым наполовину. Здесь записываются либо все имена, либо
  ни одно.

Map **копируется** (с сохранением порядка) до авторизации, и триггерится именно
копия, так что вызывающий не может изменить map — или заставить её отвечать иначе
— между проверкой и записью. `null` в ключе или значении отклоняется
`NullPointerException`, в сообщении которого названа виновная запись («trigger
value for '&lt;name&gt;'»). Пустая map ничего не триггерит и возвращает `false`, но
на закрытом движке бросает `IllegalStateException`, как и любой другой вызов, а не
тихо возвращает `false`.

### Почему `query` отклоняет не-`Routable` сообщения

`aware.query(caller, msg)` должен знать целевой тенант *до* диспетчеризации, чтобы
авторизовать. `Routable`-сообщение несёт `targetProcess()`, поэтому тенант
известен. Не-`Routable` сообщение было бы маршрутизировано по типу *внутри* движка
в процесс, который обёртка не проверяла — дыра fail-open. Поэтому `query`
отклоняет не-`Routable` сообщения с `TenantAccessDeniedException`; для явной
адресации используйте `queryProcess(caller, name, msg)`.

Обёртка читает `targetProcess()` **один раз**, авторизует это имя и отправляет
запрос ровно в этот процесс, так что сообщение не может назвать один процесс для
проверки и другой — для отправки.

## Жизненный цикл тенанта

`processesOf(caller, tenant)` отвечает на тот же вопрос, ничего не меняя: он
возвращает имена процессов тенанта в текущем графе (без глобальных) и бросает
`TenantAccessDeniedException` для вызывающего, которому этот тенант не
доверен, — поэтому через него нельзя разведать процессы чужого тенанта. На
закрытом движке он бросает `IllegalStateException` («Engine &lt;id&gt; is closed»), как и
любой другой вызов обёртки.

Вызывающий должен быть авторизован для тенанта (`authzPolicy`). Каждый вызов
действует на процессы тенанта в текущем графе (глобальные не затрагиваются) и
возвращает их имена. **Проверяйте возвращённое множество**: пустое множество
значит, что резолвер не относит к этому тенанту ни один работающий процесс
(например, id тенанта содержит разделитель при строгом резолвере по умолчанию
`suffixAfter("_")`), и ничего не было поставлено на паузу, возобновлено или
удалено.

```java
// Только чтение: на какие процессы подействуют вызовы ниже.
Set<String> names = aware.processesOf(alice, pub1);   // для bob — TenantAccessDeniedException

// Пауза: остановить процессы тенанта, сохранив их состояние.
aware.pauseTenant(alice, pub1);    // запросы к ним → QueryRejectedException ("paused";
                                   //   "<name> is shutting down", пока пауза дренирует процесс)
aware.resumeTenant(alice, pub1);   // тёплая загрузка сохранённого состояния, без init
                                   // (+ глобальные потребители, стоящие на паузе только из-за них,
                                   //    если alice проходит globalTriggerPolicy)

// Удалить насовсем: замена графа на лету без процессов тенанта.
aware.removeTenant(alice, pub1);   // состояние отозвано; при возврате тенанта — холодный init

// Отключение нескольких тенантов: одна замена графа на всех.
aware.removeTenants(admin, List.of(pub1, pub2, pub3));
```

| | `pauseTenant` / `resumeTenant` | `removeTenant` |
|---|---|---|
| Процессы | остановлены, остаются в графе | удалены из графа |
| Сохранённое состояние | сохраняется — resume загружает тёпло | отзывается (`LogDead`) — при возврате холодный init |
| Запросы в это время | `QueryRejectedException` ("paused"; запрос, пришедший одновременно с паузой, может вместо этого получить "&lt;name&gt; is shutting down", пока процесс останавливается) | неизвестный процесс |
| Триггеры / изменения зависимостей в это время | запоминаются: при resume процесс переинициализируется | — |
| Рестарт JVM | пауза сохраняется в логе: процессы остаются на паузе до resume | остаются удалёнными, если ставить граф без них |

!!! warning "Отключение тенанта: отсутствие в графе ничего не отзывает"
    Если при рестарте поставить граф **без** процессов тенанта, их состояние не
    отзывается: для узла, которого просто нет в графе, `LogDead` не пишется.
    Создайте позже тенанта с тем же id — и его процессы **тёпло загрузят
    состояние старого тенанта** (если только его тем временем не выбросил
    снапшот — снапшот хранит состояние лишь процессов текущего графа). Чтобы
    отозвать тенанта окончательно, вызовите `removeTenant` (или
    `Engine.remove`): он пишет `LogDead` для каждого его процесса, и
    при возврате тенанта будет холодный init.

    Отозвать — не значит удалить: отозванное состояние остаётся в живом логе до
    следующего [снапшота](../concepts/snapshots.md) и в его архивах, пока их не
    удалит [`purgeArchives`](../concepts/snapshots.md). Если данные тенанта нужно
    действительно удалить: `removeTenant`, затем `engine.snapshot()`, затем
    `engine.purgeArchives(0)` (или такой `keepHistory`, какой допускает ваша
    политика хранения). Так удаляются и определения процессов тенанта (их
    сохранённые `param`); с `FileLogBackend` удалите также файлы
    `<log>.truncated.<millis>`, которые `purgeArchives` не трогает — см.
    [Безопасность](../security.md#data-retention). Параметры хранятся открытым
    текстом, поэтому никогда не кладите секреты тенанта в `param`.

!!! tip "Отключайте тенантов пачками: `removeTenants`"
    Каждое удаление — это замена графа, а каждая замена графа сохраняет в лог
    **весь оставшийся граф** (`LogChangeGraph`). Поэтому удаление `N` тенантов по
    одному через `removeTenant` пишет `N` чуть уменьшающихся копий графа — рост
    лога квадратичен по `N`, и крупное отключение (скажем, тысячи тенантов из
    графа в десятки тысяч процессов) превращается в гигабайты.
    `removeTenants(caller, tenants)` удаляет процессы всех переданных тенантов
    одним `Engine.remove`: один `LogChangeGraph` и по `LogDead` на
    процесс. Авторизация — «всё или ничего»: если вызывающему нельзя управлять
    хотя бы одним из тенантов, ничего не удаляется. Разбивайте задачу отключения
    на пачки (сотни тенантов за вызов), а не вызывайте `removeTenant` в цикле.

!!! note "Запомненный триггер применяется асинхронно"
    Триггер (или изменение реактивной зависимости), пришедший, пока тенант стоял
    на паузе, при возобновлении проигрывается обычным путём триггеров, то есть
    после [`dedupWindow`](../concepts/reactive-cascade.md#окно-дедупликации).
    Поэтому запрос, отправленный сразу после возврата из `resumeTenant`, ещё
    примерно один `dedupWindow` может получить ответ из состояния до триггера,
    пока reinit не выдаст новый Sid. Если нужно именно состояние после триггера,
    дождитесь нового Sid (`introspect()`/`onSidPromotion`).

Оба механизма построены на вызовах движка, которые можно использовать и без
тенантов: `Engine.pause`, `Engine.resume`,
`Engine.remove`.

### Добавление тенанта на лету { #adding-a-tenant-at-runtime }

Вызова «добавить тенанта» у обёртки нет: подключение тенанта — это замена
графа, добавляющая его процессы. Делайте её через
[`Engine.updateGraph`](../concepts/graph-swap.md#read-modify-write-updategraph):
он читает установленный граф и ставит вашу изменённую копию под
control-lock'ом движка:

```java
engine.updateGraph(current -> {
    var nodes = new LinkedHashMap<>(current.nodes());
    // ProcessNode(name, dependencies, param, initFactory, loadFactory)
    nodes.put("Stations_PUB3", new ProcessNode("Stations_PUB3",
            List.of(Dependency.reactive("Units")),   // глобальный процесс, уже установленный
            "PUB3",                                  // param: Serializable, неизменяемый, с equals (или null)
            () -> new StationsInit("PUB3"),          // ваш ProcessInitializer
            () -> new StationsLoad("PUB3")));        // ваш ProcessLoader
    return new Graph(current.top(), nodes, current.typeRouting());
});
```

Узлы тенанта создавайте как `ProcessNode`, а не через `GraphBuilder`:
`GraphBuilder.build()` возвращает `Graph`, а его конструктор проверяет
**полный** граф, поэтому фрагмент, чьи узлы зависят от глобальных процессов
вроде `Units`, падает с «node 'Stations_PUB3' depends on missing 'Units'».
Конструктор `Graph` в примере выше проверяет уже объединённый граф
(отсутствующие зависимости, циклы, статические маршруты). Чтобы маршрутизировать
новый тип запроса, скопируйте `current.typeRouting()` в map и добавьте для него
`QueryRoute.Static` / `QueryRoute.Dynamic`. В Kotlin `Graph.extend { … }` /
`engine.extendGraphAwait { … }` из `fom-kotlin` делают это объединение за вас
через DSL — новые узлы могут зависеть от существующих по имени (см.
[Kotlin DSL](kotlin-dsl.md)).

**Не** пишите это как `engine.newGraph(withTenant(engine.currentGraph()))`.
Такой read-modify-write не атомарен: `removeTenant` (этого или другого
тенанта), выполнившийся между чтением `currentGraph()` и `newGraph`,
отменяется устаревшей копией — процессы удалённого тенанта возвращаются в граф
(с холодным init, так как их состояние было отозвано), и запросы к ним снова
проходят. `updateGraph` не пускает между чтением и установкой ни один другой
вызов control plane — `newGraph`, `remove`/`removeTenant`,
`pause`/`pauseTenant`, …

!!! warning "`Dead`-узел другого тенанта заставляет онбординг ждать и бросать исключение"
    Замена графа заодно перезапускает каждый неизменённый узел в состоянии
    `Dead` (так повтор того же графа его восстанавливает). Поэтому если у
    **другого** тенанта есть `Dead`-узел — например, его init исчерпал бюджет, —
    `updateGraph`, который лишь добавляет здорового нового тенанта, снова
    запускает этот `Dead`-узел, ждёт его до полного бюджета старта
    (`initTimeout` + `loadTimeout`) и затем бросает **его** сбой
    (например, его `InitializationTimeoutException`). Новый тенант при этом
    установлен: его узлы стартуют параллельно с `Dead`-узлом и находятся в
    `Serving`. Не полагайтесь только на исключение — проверьте
    `aware.processesOf(caller, newTenant)` и `engine.introspect()`, чтобы
    увидеть, что на самом деле обслуживает. Чтобы избежать ожидания, сделайте
    `removeTenant` (или `pauseTenant`) тенантов с `Dead`-узлами до подключения
    новых.

После рестарта движок поднимает на паузе и глобальный процесс, зависящий от
тенантного процесса на паузе, — это пауза
[из-за зависимости](../concepts/graph-swap.md#удаление-пауза-и-возобновление-процессов),
такие процессы возвращает `Engine.pausedByDependency()`. `resumeTenant`
возобновляет и такой глобальный процесс — как только ни одна из его
зависимостей больше не на паузе, и дальше по цепочке таких глобальных
процессов, — но только для вызывающего, которого принимает
`globalTriggerPolicy`: глобальный процесс общий для всех тенантов. Для
остальных он остаётся на паузе, пока его не возобновит оператор. Глобальные
процессы возобновляются через атомарный
[`Engine.resumeUnblocked`](../concepts/graph-swap.md#удаление-пауза-и-возобновление-процессов)
— только те, что всё ещё на паузе из-за зависимости и не заблокированы, —
поэтому глобальный процесс, который оператор поставил на паузу намеренно (даже
одновременно с вызовом), `resumeTenant` никогда не возобновляет. Если старт
глобального процесса отменила другая операция (например, `pause`
оператора), `resumeTenant` не бросает исключение: этот процесс остаётся на
паузе. Если глобальный процесс не запустился по любой другой причине,
`resumeTenant` бросает `RuntimeException` уже после того,
как собственные процессы тенанта возобновлены; этот глобальный процесс остаётся
на паузе, и повторный вызов `resumeTenant` пробует снова.

Все три вызова повторяют отказ, вызванный конкурентным изменением графа: если
движок отказал с `IllegalArgumentException`, потому что другой вызов тем
временем изменил граф (например, два одновременных `removeTenant`), вызов
повторяется для процессов, которые у тенанта есть сейчас. Конкурентное
повторное удаление возвращает имена, которые оно удалило (возможно, ни одного),
а не падает. Больше ничего не повторяется.
Они следуют общему правилу конкурентности замены графа: авторизованный
`pauseTenant`/`removeTenant`, отменяющий запуск узла, заставляет вызов, который
ждёт этот запуск, упасть с `InitInProgressException` («Init of process
'&lt;name&gt;' was cancelled») — конкурентный `newGraph`, заблокированный на
**первом** init узла, и так же `resumeTenant` того же тенанта, который ещё
запускает этот узел (см. [Замена графа](../concepts/graph-swap.md#конкурентность)).
`newGraph` нужно повторить; `resumeTenant`, проигравшему `removeTenant`,
возобновлять уже нечего.

!!! warning "Вызовы жизненного цикла всех тенантов выполняются по одному"
    `pauseTenant`, `resumeTenant` и `removeTenant` идут через
    `Engine.pause`/`resume`/`remove`, которые
    сериализуются на управляющей блокировке движка (вместе с `newGraph` и
    `updateConfig`). `resumeTenant` — как и любой вызов, запускающий узлы, —
    ждёт каждый запускаемый узел до `initTimeout` + `loadTimeout`,
    поэтому **медленный или зависший resume одного тенанта держит
    `pauseTenant`/`resumeTenant`/`removeTenant` всех остальных тенантов** на
    это время. То же и с остановкой: `pauseTenant`/`removeTenant` тенанта, чьи
    вычисления зависли, ждёт их слива — до собственного дедлайна запроса
    (`queryTimeout`) или бюджета `cleanupTimeout`, что наступит раньше, —
    и всё это время держит вызовы жизненного цикла остальных тенантов.
    Не вызывайте `pauseTenant`/`removeTenant` синхронно из колбэка
    `EngineObserver` об одном из процессов этого тенанта: если колбэк
    выполняется на диспетчере этого процесса, вызов сразу бросает
    `IllegalStateException` («pause('X') called on that process's own
    dispatcher …») и ничего не ставит на паузу — передайте его другому потоку
    (см. [Остановка процесса из колбэка](observability.md#stopping-from-a-callback)).
    `query`, `queryProcess`, `trigger` и `processesOf` эту блокировку
    не берут, и запросы ею не задерживаются. Но `trigger` всё же может ждать: он
    дописывает `LogTrigger`, а пока resume сканирует лог (что не пускает
    снапшоты), снапшот, вставший в очередь к шлюзу лога, заставляет новые
    добавления ждать **за ним** — шлюз это нечестная (non-fair) read/write
    блокировка, — так что такой `trigger` вернётся только после скана resume и
    затем снапшота.

!!! warning "`resumeTenant` читает весь лог"
    Чтобы найти состояние для тёплой загрузки, `resumeTenant` (как и
    `Engine.resume`) сканирует и десериализует **весь** лог — а не
    только события тенанта (хотя записанные param декодируются только у
    возобновляемых узлов), — удерживая управляющую блокировку (и не давая
    снапшоту начаться). Поэтому его стоимость растёт с **общей** длиной лога,
    каким бы маленьким ни был тенант, и всё это время он держит вызовы
    жизненного цикла остальных тенантов. Держите лог ограниченным с помощью
    [`SnapshotPolicy`](../concepts/snapshots.md#автоматически--snapshotpolicy)
    (например, `SizeBasedSnapshotPolicy`).

!!! warning "Широкие графы на файловом бэкенде"
    В `FileLogBackend` каждое долговечное изменение — одно синхронное
    добавление (`fsync`), и добавления идут по одному. Каждый узел, который
    вызов тенанта запускает, каскадно переинициализирует или останавливает,
    пишет хотя бы одну запись (тёплый старт — `LogLoaded`, холодный —
    `LogInitialized` + `LogLoaded`, остановка при `close()` — `LogCleanedUp`),
    так что операция над N узлами стоит примерно N fsync'ов или больше. При
    тысячах узлов это **секунды на операцию** на файловом бэкенде. `close()`
    останавливает узлы одной глубины зависимостей вместе, с общим дедлайном
    `cleanupTimeout`, поэтому очень широкий уровень может его превысить
    и записать WARN'ы `… did not finish stopping within its cleanup budget …`.
    Бюджет производительности из README (старт 1000 узлов < 5 с) измерен на
    `InMemoryLogBackend`, который не делает ввода-вывода.

!!! warning "Резолвер опрашивается для каждого процесса при каждом вызове"
    `processesOf`, `pauseTenant`, `resumeTenant` и `removeTenant` находят
    процессы тенанта, вызывая `TenantResolver` для **каждого неглобального узла
    текущего графа** (после одной проверки `authzPolicy` для тенанта). Поэтому
    резолвер, который возвращает `null` (`IllegalStateException`) или бросает
    исключение хотя бы для **одного** узла, ломает эти вызовы для **всех**
    тенантов — отказ в закрытую сторону, — а медленный резолвер замедляет их
    все. После возобновления процессов тенанта `resumeTenant` вычисляет
    `globalTriggerPolicy`, если в графе есть глобальные процессы, даже когда ни
    один из них не зависит от этого тенанта: политика, бросившая исключение,
    заставляет `resumeTenant` бросить его, хотя процессы тенанта уже
    обслуживают запросы.

!!! note "Глобальный процесс, оставшийся на паузе, через обёртку не виден"
    После `resumeTenant` от вызывающего **без** `globalTriggerPolicy` глобальный
    процесс, стоящий на паузе из-за зависимости, так и остаётся на паузе, а
    тенантное представление обёртки его не показывает (оно перечисляет только
    процессы тенанта). `Engine.pausedByDependency()` — **единственный** способ
    их увидеть, а `TenantAwareEngine` намеренно скрывает обёрнутый движок,
    поэтому храните собственную ссылку на `Engine`, который вы передали в
    `TenantAwareEngine`, и вызывайте на нём `pausedByDependency()`, чтобы
    увидеть, какие глобальные процессы всё ещё ждут оператора.

`removeTenant` наследует отказ `Engine.remove` опустошать граф: если
тенанту принадлежат *все* процессы текущего графа, вызов бросает
`IllegalArgumentException` («Removing [...] would leave an empty graph») и ничего
не удаляет — вместо этого закройте движок.

!!! warning "Зависимости через границу тенанта"
    Пауза или удаление падают с `IllegalArgumentException`, если процесс, который
    продолжит работать, зависит от процесса тенанта. Держите глобальные процессы
    независимыми от тенантных. Зависимость процесса одного тенанта от процесса
    **другого** тенанта при построении графа тоже не отвергается, но тогда
    `pauseTenant`/`removeTenant` тенанта-поставщика падают с сообщением движка,
    в котором назван зависящий процесс другого тенанта («Cannot pause
    '&lt;producer&gt;': '&lt;dependent&gt;' depends on it and would keep
    running», «Cannot remove '&lt;producer&gt;': '&lt;dependent&gt;' depends on
    it»). Точно так же `resumeTenant` тенанта зависящего процесса, пока тенант
    поставщика ещё на паузе, падает с сообщением, в котором назван поставщик
    другого тенанта («Cannot resume '&lt;dependent&gt;': its dependency
    '&lt;producer&gt;' is still paused»). Не стройте рёбер между тенантами.

!!! warning "Лидерство"
    Вызовы жизненного цикла записывают своё изменение в лог, поэтому
    `pauseTenant`/`resumeTenant`/`removeTenant` — как и `aware.trigger` — бросают
    [`LeadershipLostException`](../reference/exceptions.md#leadership) («lost
    leadership while persisting …»), если логом владеет другой инстанс. Сама
    отклонённая запись в лог не попала, и процессы тенанта продолжают обслуживать
    запросы из состояния в памяти. Два вызова могут быть прерваны на середине и
    тогда прямо об этом сообщают: `removeTenant`, заменивший граф, но не сумевший
    списать состояние удалённых процессов, **называет эти процессы** (изменение
    графа остаётся в силе; их состояние в логе живо, и его подхватит следующий
    лидер), а `pauseTenant`, прерванный между процессами, **называет то, что уже
    поставил на паузу**. См.
    [операции, применённые наполовину](../reference/exceptions.md#leadership-half-applied).

## Эксплуатация множества тенантов

### Цена онбординга: каждое изменение графа пишет весь граф

Каждый `newGraph`/`updateGraph`, меняющий граф, дописывает один
`LogChangeGraph` со **всеми** узлами нового графа — имя, зависимости и
сериализованный `param`, — а не только с добавленными. Онбординг тенантов по
одному через `updateGraph` поэтому пишет 1 + 2 + … + N определений узлов:
**O(N²) байт лога** на N тенантов. `SizeBasedSnapshotPolicy` здесь не
спасает: она считает *события*, а не байты, так что несколько сотен таких
записей могут занять гигабайты, прежде чем она сработает. Вместо этого:

- онбордьте **пачками** — один `updateGraph`, добавляющий узлы многих
  тенантов;
- держите `param` **маленькими** (id, по которому ищется конфигурация, а не
  сама конфигурация);
- вызывайте `engine.snapshot()` после массового онбординга — снимок сохраняет
  только текущий граф.

### Храните свой список тенантов

Движок не умеет восстановить граф из лога: `LogChangeGraph` хранит структуру
и параметры, но не фабрики и не маршруты по типам — они живут в вашем коде.
После рестарта граф заново устанавливает **ваше приложение**, поэтому оно
должно само хранить, какие тенанты существуют (в своей БД или конфигурации), и
строить узлы каждого тенанта по этому списку до вызова `newGraph`. Пропущенный
тенант не выводится из эксплуатации — см.
[жизненный цикл тенанта](#жизненный-цикл-тенанта) выше, — но и не работает.

### Провижининг обходит авторизацию обёртки

Онбординг идёт через «сырой» `Engine` (`updateGraph`), который ничего не знает
о вызывающих и `authzPolicy`. Если тенанты могут сами запускать свой
провижининг, проверяйте, что вызывающий владеет id тенанта — и что id не
совпадает с существующим тенантом или глобальным процессом, — **сами**, до
вызова `updateGraph`.

### Триггеры от тенантов

Каждый `aware.trigger(...)` — это durable-запись в лог (`fsync` на файловом
бэкенде), сделанная **до** того, как окно дедупа схлопнет повторы, поэтому
тенант, триггерящий в цикле, тратит пропускную способность лога всех
тенантов, хотя его процесс переинициализируется лишь раз за окно. Ограничивайте
частоту триггеров, доступных тенантам, по каждому тенанту (и предпочитайте
[пакетный триггер](#batch-trigger)); см.
[Триггеры](../concepts/triggers-and-watchers.md#триггеры).

### Смена политики авторизации на лету

API для замены `authzPolicy` (или `globalTriggerPolicy`) у построенной обёртки
нет. Можно построить новый `TenantAwareEngine` над тем же `Engine` или передать
политику, которая читает вашу изменяемую ссылку. Во втором случае учтите, что
обёртка вычисляет политику **для каждого имени**: [пакетный
триггер](#batch-trigger) вызывает её по разу на каждое имя пакета, поэтому
политика, заменённая во время проверки пакета, может быть видна в двух версиях —
часть имён авторизована старой, остальные новой. Если это важно:

- внутри предиката читайте ссылку **один раз** и решайте по этому снимку, чтобы
  одно вычисление никогда не смешивало две версии;
- пакет, который нужно решить по одной версии, сначала проверьте сами по одному
  снимку, а затем вызывайте `aware.trigger(caller, batch)`.

```java
AtomicReference<Policy> current = new AtomicReference<>(Policy.initial());

var aware = TenantAwareEngine.builder(engine)
    .authzPolicy((caller, tenant) -> {
        Policy p = current.get();              // один снимок на вычисление
        return p.allows(caller, tenant) && !p.suspended(tenant);
    })
    .build();

current.set(reloadedPolicy);                   // действует со следующего вычисления
```

### Общие глобальные процессы: одна переинициализация на всех тенантов

Глобальный процесс общий для всех тенантов, и его переинициализация тоже.
Триггер (или изменение зависимости) у глобального процесса снова запускает
`init` — один раз для всех тенантов. Что тенанты видят в это время, зависит от
[стратегии reinit](../concepts/process-lifecycle.md#переинициализация):

- **`KEEP_OLD` (по умолчанию).** Старая версия глобального процесса продолжает
  отвечать на каждый доходящий до него запрос — напрямую или через `compute`
  тенантского процесса, вызывающий `ctx.query`, — для всех тенантов, пока
  новая версия не загружена; затем все тенанты разом переходят на неё, а
  зависящие от него процессы переинициализируются после него. Если
  переинициализация не удалась, старая версия продолжает обслуживать **всех
  тенантов**: глобальный процесс помечается `stale`, а reinit
  [автоматически повторяется](../concepts/process-lifecycle.md#when-a-re-init-fails).
  Цена — память: пока строится новая версия, в памяти держатся и старая, и новая.
- **`RELEASE_FIRST`.** Состояние глобального процесса сначала выводится; всё
  время переинициализации каждый доходящий до него запрос **ждёт**, сразу для
  всех тенантов. Если переинициализация окончательно падает, глобальный процесс
  уходит в `Dead` **для всех тенантов**.

Поэтому:

- давайте глобальным процессам **стабильные** зависимости и триггерьте их
  редко — не из путей, доступных тенантам (`globalTriggerPolicy` по умолчанию
  никого не пускает);
- оставляйте глобальные процессы на `KEEP_OLD`, если только один из них не
  слишком велик, чтобы держать его дважды; переводя глобальный процесс на
  `RELEASE_FIRST`, делайте его `init` **устойчивым**: повторяйте обращение к
  источнику в пределах бюджета и откатывайтесь к предыдущему значению, а не
  падайте.

### Бюджеты общие для всего движка

`initTimeout`, `loadTimeout`, `cleanupTimeout` и границы
backoff живут в `EngineConfig` и действуют на **каждый** узел: бюджета на узел
или на тенанта нет. Тенант, чьим данным нужен 10-минутный init, навязывает
этот бюджет всем (и заодно откладывает момент, когда сдаётся зависший init
любого тенанта). Обходной путь — **отдельный движок на класс тенантов**
(например, маленькие / большие), у каждого свой `EngineConfig` и свой лог.
Цена: глобальные процессы принадлежат движку, поэтому каждый движок держит —
инициализирует, хранит и обслуживает — **свою копию** каждого нужного тенантам
глобального процесса и переинициализирует её сам.

### Вычисления тенантов не изолированы

`compute`, `init` и `load` всех тенантов выполняются в виртуальных потоках,
которые делят единственный пул carrier-потоков JVM размером с число ядер CPU.
Вычисление одного тенанта, которое блокируется, будучи **закреплённым**
(pinned — внутри `synchronized` на JDK 21), или крутит **CPU-bound** цикл, не
паркуясь, держит carrier; нескольких таких хватит, чтобы остановить всех
тенантов — их запросы упираются в таймаут, их остановки выжидают весь бюджет
очистки. Бюджета потоков на тенанта нет; как не допускать закрепления и где
выполнять тяжёлую для CPU работу, см.
[На каких потоках выполняется ваш код](../concepts/process-lifecycle.md#virtual-threads).

### Перенос тенанта на другой движок

API экспорта/импорта нет, а приостановленный процесс нельзя опросить
(`QueryRejectedException`), так что работающий движок состояние тенанта не
отдаст. Что можно сделать:

1. Добавить узлы тенанта в **целевой** движок (`updateGraph`) — там они
   холодно инициализируются из исходных данных тенанта. `updateGraph`
   блокируется, пока они не завершат старт; проверьте через `introspect()`,
   что они в `Serving` (а не `Dead`), прежде чем идти дальше.
2. Переключить маршрутизацию, чтобы вызовы тенанта шли в целевой движок.
3. Вызвать `removeTenant` на **исходном** движке, чтобы вывести там его
   состояние, и убрать тенанта из списка исходного движка.

Если ваш `init` не умеет восстановить состояние из внешнего источника,
скопируйте сохранённые ячейки из лога исходного движка сами. Лог читается
публичным API `io.fom.log`, движок для этого не нужен:

1. **Остановите исходный движок** (`close()`), чтобы копируемое состояние было
   окончательным, — до `removeTenant`, который это состояние выводит. Скопируйте
   файл его лога и работайте с копией: открытие `FileLogBackend` берёт
   блокировку файла и отрезает оборванный последний кадр.
2. Просканируйте копию и оставьте для каждого процесса тенанта **последний
   `LogInitialized`, за которым не следует `LogDead` этого процесса**, — то
   состояние, которое загрузил бы тёплый старт:

    ```java
    Map<String, LogInitialized> live = new HashMap<>();
    try (var log = new FileLogBackend(copyOfSourceLog)) {
        log.forEachBetween(0, log.length(), event -> {
            switch (event) {
                case LogInitialized init when init.processName().endsWith("_" + tenant) ->
                        live.put(init.processName(), init);
                case LogDead dead -> live.computeIfPresent(dead.sid().processName(),
                        (name, init) -> dead.sid().clock() >= init.clock() ? null : init);
                default -> { }
            }
        });
    }
    // live.get(name).properties() — это Map<String, byte[]>, которую вернул init процесса
    ```

   На `PostgresLogBackend` вместо этого сделайте запрос к таблице и декодируйте
   payload, как описано в разделе [CDC](persistence-backends.md#consuming-the-log-with-cdc).
3. Положите эти ячейки туда, откуда их прочтёт целевой движок, и пусть `init`
   целевого узла возвращает их (`CompletableFuture.completedFuture(cells)`)
   вместо вычисления, — затем добавьте узлы в целевой движок (`updateGraph`) и
   переключите маршрутизацию, как в первом списке выше. Его `load` построит
   процесс из тех же байтов.

Оговорки: ячейки — это байты, которые записал **код вашего процесса**, поэтому
на целевом движке должна работать версия этого кода (и классов, которые он в них
сериализует), способная их прочитать; `SerDe` движка в ячейках не участвует, но
должен декодировать параметры целевого графа. Целевой движок записывает ячейки
как свежий `init` (новый Sid) — история источника, паузы и отложенные триггеры
не переносятся.

### Квоты и размер состояния тенанта

Размера состояния процесса нет ни в `introspect()`, ни в каком-либо колбэке
`EngineObserver`, поэтому квоту на хранимое состояние придётся мерить самим.
Оберните инициализатор: ячейки, которые он возвращает, — это ровно то, что
хранит лог.

```java
static ProcessInitializer measured(String name, ProcessInitializer delegate) {
    return ctx -> delegate.init(ctx).thenApply(cells -> {
        long bytes = cells.values().stream().mapToLong(c -> c.length).sum();
        stateBytes.put(name, bytes);          // ваш gauge / проверка квоты
        if (bytes > LIMIT) throw new IllegalStateException(name + " state is " + bytes + " bytes");
        return cells;
    });
}
```

Упавший `init` повторяется и может закончиться в `Dead` (см.
[жизненный цикл процесса](../concepts/process-lifecycle.md#повторы-backoff-таймауты)),
поэтому бросайте исключение только для жёсткого лимита; в остальных случаях
записывайте и алертите.

## Отказ в доступе

Отклонённый вызов завершает возвращённый stage с `TenantAccessDeniedException`
(для `query`/`queryProcess`) или бросает его напрямую (для `trigger` и вызовов
жизненного цикла). Если сами `authzPolicy` или резолвер бросают исключение в
`query` / `queryProcess`, это исключение тоже завершает возвращённый stage (по-прежнему
fail-closed), а не бросается синхронно. Авторизация происходит **раньше**, чем
дело вообще доходит до движка, поэтому закрытый движок не меняет вердикт:
неавторизованный вызывающий всё равно получит `TenantAccessDeniedException` —
`anon` ниже получает именно его, закрыт движок или нет, — и только
*авторизованный* вызывающий получит `IllegalStateException` («Engine &lt;id&gt;
is closed») от движка:

```java
aware.query(anon, new GetStations("PUB1"))
    .whenComplete((r, err) -> {
        if (err instanceof TenantAccessDeniedException) { /* 403 */ }
    });
```

[Пакетный триггер](#batch-trigger) отклоняется целиком, и не триггерится ничего —
даже собственные имена вызывающего:

```java
// alice может работать только с PUB1: из-за Stations_PUB2 весь пакет бросает
// TenantAccessDeniedException, и Stations_PUB1 тоже НЕ триггерится.
aware.trigger(alice, Map.of(
    "Stations_PUB1", new RefreshSignal("x"),
    "Stations_PUB2", new RefreshSignal("y")));
```

## Сводка дефолтов

| Настройка | По умолчанию | Следствие |
|---|---|---|
| `tenantResolver` | строгий `suffixAfter("_")` | разрешается только `<база>_<тенант>`; неоднозначные имена — отказ |
| `authzPolicy` | `(c, t) -> false` | **запрет всего**, пока не настроено |
| `globalProcesses` | нет | процесс без тенанта — отказ |
| `globalTriggerPolicy` | `c -> false` | глобальные процессы — только для запросов |
| не-`Routable` `query` | отклоняется | используйте `queryProcess` |

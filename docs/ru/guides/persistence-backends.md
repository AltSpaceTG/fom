# Бэкенды хранения

`LogBackend` — это место, где живёт [append-only лог](../concepts/the-log.md). Три
поставляются в комплекте; можно написать свой против SPI.

| Бэкенд | Модуль | Хранит? | Лидерство | Для чего |
|---|---|---|---|---|
| `InMemoryLogBackend` | `fom-core` | нет | внутри процесса | тесты, быстрый старт, эфемерное состояние |
| `FileLogBackend` | `fom-core` | да (файл) | ОС-блокировка файла | одноузловое долговечное состояние |
| `PostgresLogBackend` | `fom-jdbc` | да (таблица) | `pg_advisory_lock` | координация лидерства между узлами |

Все три соблюдают один [контракт `LogBackend`](../concepts/the-log.md#spi-logbackend)
(атомарный append, один лидер, параллельные чтения, монотонные clock'и,
сохраняемые `compact`) и
проверяются общим `LogBackendContractTest`.

## InMemoryLogBackend

```java
try (var backend = new InMemoryLogBackend()) { … }
try (var backend = new InMemoryLogBackend("my-log-id")) { … }
```

На основе `CopyOnWriteArrayList`. Ничего не переживает JVM — каждый старт
холодный. Идеален для тестов.

## FileLogBackend

```java
void run() throws IOException {   // конструктор объявлен как `throws IOException`
    try (var backend = new FileLogBackend(Path.of("/var/lib/fom/log.bin"))) { … }
}
```

`FileLogBackend(Path)` — единственное место в API с **проверяемым
исключением**: он бросает `java.io.IOException`, если файл не удаётся открыть
или воспроизвести, — поэтому объемлющий метод обязан его объявить или обработать
(в маленькой программе достаточно `public static void main(String[] args) throws Exception`).
Лог, который **уже открыт** — его `.lock` держит другой процесс или другой бэкенд
в этой же JVM, — отклоняется непроверяемым `IllegalStateException`
(`Cannot acquire leader lock on … — another process holds it` /
`… is held by another thread in this JVM`), а не `IOException`.
**Имя файла** лога длиннее 224 байт (UTF-8) отклоняется сразу с
`IllegalArgumentException`: бэкенд держит соседние файлы с именем `<name>` плюс
суффикс длиной до 31 байта (`.archived.<13 цифр millis>.partial`; а также
`.truncated.<millis>`, `.tmp`, `.lock`), и имя, которое укладывается в предел
`NAME_MAX` в 255 байт, но не вместе с суффиксом, открылось бы, а затем ломало бы
каждый снапшот — и делало бы оборванный хвост невосстановимым.

- Каждое событие обрамлено `[int length][int CRC32][payload]`; файл начинается с
  4-байтовой магии (`FOM\1`), чтобы неверный файл падал явно.
- При открытии весь файл сканируется. Отрезается только неполный **последний**
  фрейм — то, что оставляет крах посреди записи; отброшенные байты сохраняются
  рядом с логом как `<name>.truncated.<millis>`. Фрейм, выходящий за конец файла
  (или последний фрейм с неверным CRC), считается неполным, только если после
  его заголовка не найдено ни одного целого фрейма с верным CRC: append — одна
  последовательная запись с fsync, поэтому после оборванного фрейма крах не
  оставляет ничего целого, а повреждённое поле длины у фрейма в середине — оставляет.
  Учитывается только фрейм, с которого начинается структурно корректная цепочка
  фреймов до конца файла, поэтому байты внутри полезной нагрузки самого
  оборванного фрейма, похожие на фреймы (сериализованные свойства и даже целый
  лог fom, сохранённый как свойство), восстановлению не мешают. Поиск линеен по
  размеру оборванного фрейма; данные, подобранные так, чтобы вызвать чрезмерную
  работу по CRC, вместо этого проваливают открытие с `LogCorruptedException`.
  Если отброшенные байты сохранить не удаётся (обычно — кончилось место на
  диске), открытие падает с `IOException`, где названы лог, соседний файл и
  причина — `could not save the torn tail of <log> to
  <log>.truncated.<millis>: ... No space left on device`; недописанный файл
  `.truncated.*` не остаётся, а сам лог **не** изменяется. Освободите место и
  откройте его снова (совет «free some space» даётся, только если причина —
  нехватка места на диске или квоты; при любой другой причине, например
  `AccessDeniedException` на каталоге, сообщение предлагает устранить причину).
  Сохранённый хвост получает POSIX-права лога (и владельца/группу, где это разрешено).
- Неудачный `append` бросает `RuntimeException`, в сообщении которого названа и
  причина — `Append failed on <log>: java.io.IOException: No space left on device`, —
  так что она видна и там, где выводится только `getMessage()` (например,
  `NodeReport.lastException`).
- Любое другое повреждение — плохой фрейм, за которым идут ещё данные (в том
  числе фрейм в середине, чья повреждённая длина указывает за конец файла), длина
  фрейма больше лимита полезной нагрузки в 64 МиБ или целый (с верным CRC) фрейм,
  который не удаётся декодировать (подделка, класс, отклонённый allowlist'ом
  десериализации, или класс события, который эта версия не умеет читать), или
  событие, чей clock не больше, чем у предыдущего (фреймы двух линий времени,
  склеенные вместе, — split brain или бэкап, дописанный к копии; открыв такой лог,
  движок выдал бы повторно уже существующие clock'и), — заставляет конструктор
  бросить `io.fom.log.LogCorruptedException` и оставляет
  файл **нетронутым**. Это `IOException` с `offset()` (байтовое смещение первого
  нечитаемого фрейма), `readableEvents()` и `path()`. Для восстановления сделайте
  резервную копию файла, затем восстановите его или обрежьте до `offset()` байт
  (например, `truncate -s <offset> <file>`) — это отбросит все события начиная с
  этого места. [`fom-log diagnose`](cli.md#diagnose) сообщает то же смещение.
- Событие, которое бэкенд не смог бы прочитать после рестарта, не записывается:
  `append` отклоняет его с `IllegalArgumentException`. Это событие сверх лимитов
  полезной нагрузки лога: не более 64 МиБ на событие (сериализованная полезная
  нагрузка фрейма — тот же лимит, что проверяет чтение), массивы не длиннее
  10 000 000 элементов (например, свойство типа `byte[]`), не более 1 000 000
  ссылок на объекты, глубина вложенности до 64. Сообщение перечисляет эти
  лимиты. `PostgresLogBackend` выполняет ту же проверку обратного чтения, но
  отдельного ограничения размера в 64 МиБ у него нет. Если это результат init
  (`LogInitialized`), процесс сразу уходит в `Dead`, не повторяя `init`; см.
  [Жизненный цикл процесса](../concepts/process-lifecycle.md#повторы-backoff-таймауты).
- Прерывания потоков не ломают ввод-вывод: append прерванного вызывающего всё
  равно завершается (флаг прерывания восстанавливается после). Прерывание
  посреди записи закрывает канал; бэкенд открывает его заново (пишет это в лог
  на `DEBUG`), удаляет
  недописанный кадр и пишет событие ещё раз — append падает, только если его
  прервали три раза подряд, и лог в любом случае остаётся согласованным.
- **Лидерство** — эксклюзивная ОС-блокировка соседнего файла `<name>.lock`,
  берётся при конструировании. Блокировка, как и файл данных, архивы и `.tmp`,
  лежит рядом с **настоящим** файлом: путь разрешается через символические ссылки
  (для ещё не существующего лога — через родительский каталог), поэтому второй
  процесс, открывающий тот же файл по любому пути — напрямую или через симлинк, —
  падает с `IllegalStateException`, а `logId()` возвращает разрешённый путь.
  Жёсткие ссылки неотличимы: не делайте hard link на файл лога. Как и раньше,
  недостающие родительские каталоги создаются (для симлинка на ещё не созданный
  лог — каталоги цели). **Обновление при логе за симлинком:** файлы `.lock`,
  `.tmp`, `.truncated.*` и новые `.archived.*` теперь лежат рядом с настоящим
  файлом, поэтому архивы, записанные раньше рядом с симлинком, больше не
  удаляются `purgeArchives` (перенесите их к настоящему файлу или удалите); и не
  запускайте старую и новую версии на одном логе за симлинком одновременно
  (rolling upgrade) — старая блокирует `<link>.lock`, новая `<real>.lock`, и
  лидерами станут обе. **Не удаляйте файл `.lock`, пока работает движок:**
  блокировка держится на этом файле, и второй процесс мог бы создать новый,
  заблокировать его и незаметно стать лидером того же лога.
- **Не удаляйте, не переименовывайте, не подменяйте и не перезаписывайте файл
  лога, пока работает движок.** Бэкенд пишет в тот файл, который открыл, поэтому
  после `rm`, `mv` или восстановления из бэкапа поверх пути записи уходили бы в
  осиротевший файл, которого следующий запуск не увидит, — и этот запуск молча
  стартовал бы с нуля. Поэтому перед каждым append (и каждой компактизацией)
  бэкенд одним `stat` проверяет, что путь по-прежнему указывает на открытый файл
  (тот же file key, т. е. inode). Если нет, запись отклоняется с
  `IllegalStateException: log file <path> was deleted or replaced while open
  ...; refusing to append to an orphaned file`. Перезапись **на месте** inode
  сохраняет (`cp backup.bin log.bin` поверх существующего файла, `truncate`,
  дозапись другой программой), поэтому бэкенд ещё одним `fstat` проверяет, что
  файл заканчивается ровно там, где его оставила последняя собственная запись;
  если нет, запись отклоняется с `IllegalStateException: log file <path> was
  modified by something else while open (it is <n> bytes, this backend last
  left it at <m>) ...`. Перезапись на месте содержимым ровно той же длины не
  обнаруживается. По контракту SPI `LogBackend` оба случая — **временный** сбой:
  движок повторяет попытку с backoff, а затронутые процессы явно падают, когда
  исчерпан бюджет повторов фазы; ничего при этом не подтверждается. Если вернуть
  исходный файл (или его исходное содержимое) на место, запись возобновится. На
  платформах без file key (Windows) проверка file key пропускается, проверка
  размера выполняется.
- **Компактизация** записывает сжатый лог в `<name>.tmp` (с fsync), копирует
  старый в `<name>.archived.<timestamp>.partial` и атомарно переименовывает его в
  `<name>.archived.<timestamp>`, атомарно заменяет живой файл файлом
  `<name>.tmp` и делает fsync каталога, чтобы переименование было долговечным
  при потере питания. Файл `.tmp` ещё до записи данных получает POSIX-права живого
  лога, а также его владельца и группу, если процессу это разрешено (от root), так
  что лог с правами `0600` остаётся `0600` после снапшота, а не получает права по
  umask, а запущенный от root `fom-log compact` не оставляет лог, принадлежащий root
  (неудачный `chown` не от root игнорируется, права всё равно копируются). На
  файловых системах без POSIX-атрибутов это пропускается. Живой файл корректен на каждом шаге: после краха до
  замены остаётся старый лог, после неё — новый. Крах может оставить лишь
  полноразмерный `<name>.tmp` и/или недописанную копию архива `.partial`; оба
  файла (обычный файл `<name>.tmp` и `<name>.archived.<цифры>.partial`) бэкенд
  удаляет при следующем открытии лога, уже взяв блокировку, и пишет об этом в
  лог на уровне `INFO`. `purgeArchives` удаляет все файлы
  `<name>.archived.<millis>`, кроме новейших (учитываются только имена,
  оканчивающиеся цифрами), а также оставшиеся файлы `.partial`. Метка — время по
  настенным часам, но не меньше наибольшей метки существующего архива + 1, так
  что новейший архив сохраняет наибольшую метку и после перевода часов назад.
  Архиву с меткой более чем на 100 лет впереди часов не верят: это пишется в
  лог на `WARN`, и такой архив считается самым старым.

Этот бэкенд владеет своими файлами; путь — доверенный ввод от приложения.

### Размер большого лога

При открытии лог читается и десериализуется **целиком**, фрейм за фреймом (чтобы
проверить его и построить индекс), а пока лог открыт, бэкенд держит в куче
смещение и длину каждого события — по измерениям около 75 байт на событие. Лог в
5 ГБ из 21 миллиона событий потребовал около 1,6 ГБ кучи и открывался 4,4
минуты. Команды чтения [`fom-log`](cli.md) открывают копию лога так же и
требуют примерно столько же кучи (`JAVA_OPTS=-Xmx…`). Ограничивают и то и другое
[снапшоты](../concepts/snapshots.md): компактизация переписывает лог до живого
состояния, так что время открытия и размер индекса зависят от состояния и
событий после последнего снапшота, а не от всей истории. Если лог дорастает до
миллионов событий, включите снапшоты (или запустите `fom-log compact` офлайн),
а не увеличивайте кучу.

Большие записи расходуют кучу, а не нативную память: фреймы пишутся и читаются
ограниченными кусками по 256 КиБ, поэтому временные direct-буферы JDK на каждом
потоке (JDK кеширует их на всё время жизни потока) остаются маленькими при любом
размере записи, и дописывание и снапшоты записей в десятки МБ не требуют
увеличивать `-XX:MaxDirectMemorySize`. Фрейм по-прежнему попадает в индекс — и
становится видимым — только после того, как записан целиком и сброшен fsync;
сбой посреди фрейма оставляет оборванный хвост, который следующее открытие
обрезает, как и раньше.

### Резервные копии

Копируйте живой лог только при остановленном движке или через
[`fom-log`](cli.md) (его команды чтения работают с приватной копией и не трогают
оригинал). Обычный `cp` файла, в который идёт запись, может оборваться посреди
фрейма; это лишь оборванный хвост, который отрезается при открытии. Настоящая
опасность — **запустить** движок на копии, пока оригинал продолжает работать в
другом месте: тогда оба дописывают события с одинаковыми clock'ами, и ничто не
отличает две линии времени, пока кто-нибудь не склеит их (такое открытие будет
отклонено, см. выше) или не восстановит не ту. Считайте копию бэкапом, а не
вторым живым логом.

## PostgresLogBackend

`fom-jdbc`. Хранит события в одной таблице и координирует лидерство advisory-локом
Postgres — основа для [нескольких узлов](multi-node.md).

```java
import io.fom.jdbc.PostgresLogBackend;
import java.sql.SQLException;

// dataSource: пул соединений, например HikariCP
// Оба конструктора объявляют `throws SQLException`: они сразу подключаются,
// создают таблицу и берут advisory-lock.
void serve(DataSource dataSource) throws SQLException {
    try (var backend = new PostgresLogBackend(dataSource, "weather");   // таблица fom_log_weather
         var engine  = new Engine(EngineConfig.defaults(), backend, serDe)) {
        …
    }
    // или явно указать имя таблицы:
    // new PostgresLogBackend(dataSource, "weather", "fom_log_weather")
}
```

- **Имя таблицы.** Конструктор с двумя аргументами использует
  `fom_log_<logId>` и **отклоняет** `logId`, содержащий что-либо кроме ASCII-букв,
  цифр и `_`, с `IllegalArgumentException` (прежние версии заменяли такие символы
  на `_`, и `weather-eu` и `weather_eu` молча делили одну таблицу и одну
  блокировку). Конструктор с тремя аргументами вместо этого принимает явное имя
  таблицы. В обоих случаях регистр не важен (имя приводится к нижнему регистру,
  как Postgres делает с идентификаторами без кавычек): `Weather` и `weather` — один
  лог с одной блокировкой лидера. Имя, содержащее `_archived_` (зарезервировано
  для архивных таблиц), зарезервированное слово SQL или имя, уже занятое
  объектом, который не является таблицей (представление, последовательность,
  индекс, …), отклоняется с `IllegalArgumentException`.
- **Проверки таблицы при открытии.** Таблица ищется только в той схеме, где она
  создаётся (`current_schema()`, первая существующая схема `search_path`). Имя,
  которое `search_path` раньше находит в другом месте — системный каталог вроде
  `pg_class` (неявная `pg_catalog` идёт первой) или одноимённая таблица в другой
  схеме, — отклоняется с `IllegalArgumentException`, где сказано, куда оно
  разрешается. `search_path`, в котором нет ни одной существующей схемы (тогда
  `current_schema()` — null и таблицу создать негде), отклоняется с
  `IllegalStateException`, где это сказано; задайте в соединении `currentSchema`
  (или `search_path` роли) с существующей схемой. **Существующая** таблица должна быть таблицей лога (`row_id bigint`,
  `type text`, `payload bytea`, `ts_millis bigint`); всё остальное, например
  пользовательская таблица `customers`, отклоняется с
  `IllegalArgumentException: table customers exists but is not a fom log table
  (missing column row_id)`, а не падает позже на «сырой» ошибке SQL. Для **нового**
  лога должны быть свободны и имена его последовательности (`<table>_rid_seq`) и
  индекса первичного ключа (`<table>_rid_pk`), а также индекса `LogLeader`
  (`<table>_leader_ix`): они в одном пространстве имён с
  таблицами, поэтому лог `cz` нельзя создать, пока существует лог `cz_rid_seq`
  (таблица `fom_log_cz_rid_seq`). Это отклоняется с `IllegalArgumentException`,
  где назван конфликтующий объект, ещё до создания чего-либо. То же верно, когда
  два лога создаются **в один и тот же момент** и столкновение проявляется только
  в самом `CREATE` (SQLState `23505` на `pg_class_relname_nsp_index` или `42P07`):
  создание у проигравшего откатывается, и он получает то же
  `IllegalArgumentException`, а не «сырой» `PSQLException`.
- **Writable primary, пулинг сессий.** Конструктор отклоняет hot standby
  (`pg_is_in_recovery()`) и read-only-сессию (`default_transaction_read_only = on`)
  с `IllegalStateException: … the database is a read-only server (hot standby?) …`
  ещё до взятия блокировки. Лидерство — это advisory-lock уровня сессии, поэтому
  **пулинг транзакций или операторов (PgBouncer `pool_mode=transaction`/`statement`)
  не поддерживается**: он отдаёт серверную сессию с блокировкой другим клиентам, и
  лидером стал бы каждый узел; подключайтесь напрямую или через
  `pool_mode=session` (пулы внутри JVM, вроде HikariCP, подходят). Такой прокси
  конструктор отклоняет с `IllegalStateException` (в сообщении есть
  `pool_mode=session`), когда может его заметить — выданная серверная сессия уже
  держит блокировку этого лога или последовательные транзакции сообщают разные
  `pg_backend_pid()`, — но тихий пул, который раз за разом возвращает ту же
  серверную сессию, проверку проходит, так что это страховка, а не гарантия. См.
  [Несколько узлов](multi-node.md#настройка-postgres).
- **Бэкенд принадлежит вам.** `Engine.close()` не закрывает `LogBackend`.
  Закрывайте бэкенд сами (try-with-resources или `backend.close()`), чтобы
  освободить advisory-lock, иначе standby не сможет перехватить лидерство, пока
  соединение не умрёт. `close()` снимает блокировку явно (после
  `Connection.close()` пул сохраняет физическую сессию, а с ней и блокировку
  уровня сессии), при неудаче повторяет попытку несколько раз с короткой паузой и
  проверяет в той же сессии, что блокировки больше нет. Если подтвердить это не
  удаётся — скажем, каждый запрос отменяется, — он пишет `WARN` и **прерывает**
  соединение (`Connection.abort`), а не возвращает его в пул, так что сессия и
  её блокировка действительно завершаются. Уже мёртвая сессия ничего не требует.
- **Используйте пул соединений с таймаутами.** Каждый вызов
  `get`/`getBetween`/`length` берёт соединение из `DataSource`. Старт читает лог
  диапазонами по 1000 событий (`getBetween`), а не отдельным запросом на каждое
  событие, но `DataSource` без пула всё равно открывает физическое соединение на
  каждый вызов. Используйте пул, например HikariCP, и задайте таймаут получения
  соединения и таймаут сокета — для драйвера pgjdbc это `connectTimeout` и
  `socketTimeout` (у `PGSimpleDataSource` по умолчанию таймаута сокета нет). Без
  них чтения висят всё время, пока Postgres не отвечает или пул исчерпан.
  `socketTimeout` выбирайте осознанно: если база «замирает» дольше него,
  возникает ошибка уровня соединения (SQLState `08xxx`), после которой экземпляр
  отстраняется навсегда (см. [Несколько узлов](multi-node.md#failover)). Это
  возможно только для запросов, которые бэкенд посылает по **лидерской сессии**:
  записи и keepalive раз в 15 с. Чтения и `introspect()` используют
  короткоживущие соединения, поэтому health-check во время паузы не может
  стоить узлу лидерства.
- **HikariCP: лидерское соединение занято навсегда.** Лидерская сессия
  удерживается всё время жизни бэкенда, поэтому `leakDetectionThreshold`
  Hikari сообщит о ней как об утечке (`WARN` `Apparent connection leak
  detected` со стеком конструктора), когда порог истечёт, — это ожидаемо, а не
  ошибка; не включайте обнаружение утечек на пуле, выделенном под fom, или
  примите одно предупреждение на бэкенд. `maxLifetime` (и `idleTimeout`) к нему
  тоже не применяются: Hikari выводит из оборота только возвращённые
  соединения, так что лидерская сессия живёт до `backend.close()` или пока её
  не завершит сервер или сеть. Если что-то по пути (прокси, файрвол,
  `idle_session_timeout` сервера) ограничивает возраст сессии, это прекращает
  лидерство — узел отстраняется, — а не пересоздаёт соединение.
- **Размер пула: не меньше числа бэкендов + 1.** Каждый `PostgresLogBackend`
  держит **одно соединение пула всё время своей жизни** — лидерскую сессию,
  которой принадлежит advisory-блокировка и по которой идут все записи, — и
  берёт дополнительные короткоживущие соединения для чтений
  (`get`/`getBetween`/`length`), `introspect()` и подтверждений блокировки.
  Второе соединение нужно уже в конструкторе (чтобы прочитать состояние
  лидерства лога). Поэтому задайте пулу размер **не меньше числа бэкендов,
  которые его делят, + 1**, плюс запас на параллельные чтения и health-check'и;
  при `maximumPoolSize = 1` конструктор падает с `IllegalStateException`
  («could not get a second connection … size the pool to at least the number of
  backends + 1»), с собственным таймаутом пула в качестве причины, и отпускает
  взятые блокировку и соединение (таблица к этому моменту может быть уже
  создана). Слишком маленький для работающего узла пул проявляется в том, что
  чтения и `introspect()` ждут таймаута получения соединения из пула.
- **Подойдёт любой уровень изоляции по умолчанию; собственные записи бэкенда
  идут на `READ COMMITTED`.** Барьеру записи и защите append нужно, чтобы каждый
  оператор видел всё, что закоммичено до него. На `REPEATABLE READ` или
  `SERIALIZABLE` первый запрос транзакции фиксирует её снимок, и `LogLeader`,
  закоммиченный другим узлом, пока append ждёт барьер, остался бы невидим —
  смещённый лидер продолжил бы писать с дублирующимися clock. Поэтому бэкенд
  переводит лидерское соединение на `READ COMMITTED` (`setTransactionIsolation`)
  независимо от умолчания пула (HikariCP `transactionIsolation`), роли или базы
  (`default_transaction_isolation`), начинает каждую транзакцию записи с
  `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` и берёт барьер первым
  оператором, до любого запроса. При закрытии бэкенда соединение возвращается в
  пул с тем уровнем, с которым было получено. Короткоживущие соединения для
  чтений остаются на уровне пула: чтениям конкретный уровень не нужен.
- **Открытие большого лога.** Конструктор читает последнюю строку (поиск по
  первичному ключу) и последний `LogLeader` через частичный индекс
  `<table>_leader_ix ON <table> (row_id) WHERE type = 'LogLeader'` — в прежних
  версиях такого индекса не было, и ради него при каждом открытии и захвате
  лидерства сканировалась вся таблица. Новая таблица получает индекс при
  создании; **существующая** — при первом открытии этой версией (`CREATE INDEX`,
  пишется в лог на `INFO`; он блокирует писателей, а их нет, кроме держателя
  блокировки, но не читателей). Для построения нужно владение таблицей: роль,
  которой разрешены только чтение и запись, пишет `WARN` с командой
  `CREATE INDEX IF NOT EXISTS …` для владельца и открывает лог без индекса.
  Компакция уносит индекс вместе с таблицей в архив (под именем
  `<archive>_leader_ix`) и создаёт новый. Если серверный `statement_timeout`
  (или `lock_timeout` за чужой блокировкой таблицы) отменяет какой-либо из
  запросов открытия, конструктор бросает `SQLException` с тем же SQLState
  (`57014` / `55P03`), в сообщении которого сказано, что открытие отменено
  сервером, назван `statement_timeout` и приведена команда `CREATE INDEX`, — а не
  голое `canceling statement due to statement timeout`. Увеличьте таймаут для
  соединений бэкенда (например, `options=-c statement_timeout=60s` в JDBC URL)
  или постройте индекс заранее.
- **Большие события и `statement_timeout`.** Чтение диапазона сначала получает
  список окна (id строк и размеры payload — дёшево, размеры берутся из заголовка
  TOAST), а затем читает payload сериями подряд идущих строк не более 8 МиБ на
  один `SELECT`; одно событие крупнее читается отдельно. Поэтому лог из больших
  событий остаётся читаемым, и узел может перезапуститься, при серверном
  `statement_timeout`, в который укладывалась каждая запись: прежние версии
  читали до 1000 событий одним `SELECT`, и он мог не уложиться в таймаут (5
  событий по 60 МБ при `statement_timeout = 1s`: все записи прошли, рестарт
  упал с `getBetween failed`). Серия, которую всё же отменили (SQLState
  `57014`), перечитывается половинами, вплоть до одной строки; ошибкой чтение
  завершится, только если в таймаут не укладывается одно событие. Каждая серия
  проверяется на то, что она из той же таблицы (по oid), что и список, поэтому
  компакция между ними обнаруживается и чтение повторяется.
- **Чтения переживают один оборванный коннект.** `length()`, `get` и
  `getBetween` идут по соединению из пула; если его серверная сессия оказалась
  мёртвой (SQLState класса `08` или `57P01`/`57P02`/`57P03` —
  `pg_terminate_backend`, рестарт сервера, сброс простаивающего соединения
  прокси), чтение повторяется **один раз** на свежем соединении, так что одно
  протухшее соединение пула больше не роняет старт движка. Чтение, которое всё
  равно упало — или не смогло получить соединение, — бросает исключение с
  причиной и её SQLState в сообщении (например,
  `getBetween(0,2) failed on fom_log_x: … (SQLState 08006)`).
- **`introspect()` ограничен по времени.** Его работа с базой (проверка
  advisory-lock и отчётный запрос) ограничена 5 с. Если Postgres
  не ответил вовремя или пул не смог выдать соединение, он пишет `WARN` (не чаще
  раза в 30 с) и возвращает последнюю известную длину — по тому же правилу, что
  и после `close()` ниже, то есть с учётом собственных append'ов экземпляра после
  последнего `introspect()` — и последние счётчики событий (длину `-1`, если она
  ни разу не была известна), а не зависает и не бросает исключение. `currentLeader` остаётся этим экземпляром, пока тот достоверно не
  потерял блокировку.
- **`introspect()` отвечает и после `close()`.** Передача лидерства standby — это
  закрытие бэкенда, поэтому health-check должен это переживать: закрытый бэкенд
  сообщает последнюю известную ему длину — прочитанную `length()`, `getBetween`
  или `introspect()` и поддерживаемую в актуальном состоянии его собственными
  append и compact (длину `-1`, если она ни разу не была известна), — и счётчики
  событий последнего `introspect()` (пусто, если его не было), с
  `currentLeader() == null` — `isLeader` равен `false` — и не открывает для
  этого ни одного соединения. Поэтому после старта движка (который читает лог)
  длина актуальна, даже если `introspect()` ни разу не вызывался; счётчики по
  типам могут от неё отставать. Любой другой вызов на
  закрытом бэкенде по-прежнему падает с `IllegalStateException`. Процессы в
  `Serving` при этом продолжают отвечать на запросы из памяти; процесс, застигнутый
  **посреди reinit** (уже после своего `LogDead`, на очистке или внутри `init`), —
  нет: каждая попытка init падает с `ERROR` «could not persist LogInitialized for
  init attempt &lt;n&gt;» плюс `WARN`, процесс остаётся в `Initializing` без Sid,
  пока не кончится бюджет init, и затем переходит в `Dead`, а запросы к нему тем
  временем уходят в таймаут (подробности — в
  [Несколько узлов](multi-node.md#failover)). **Когда вы всё-таки закроете
  движок, ждите по одному `WARN` на процесс.** Очистка каждого процесса
  добавляет в лог информационное событие `LogCleanedUp`, а на закрытом бэкенде
  эта запись падает, поэтому передача лидерства в таком порядке заканчивается
  одним `WARN` на процесс на `engine.close()` — о том, что бэкенд закрыт. Ничего
  не теряется: событие информационное, FSM всё равно доходит до `Dead`, а
  `close()` завершается нормально.
- **Отстранение видно в `introspect()`.** `introspect()` проверяет, что backend
  лидерской сессии всё ещё держит advisory-lock — на короткоживущем соединении
  из `DataSource`, никогда на самой лидерской сессии, поэтому health-check
  только для чтения не может ни сломать эту сессию, ни отстранить узел.
  Отстранённый экземпляр (его
  сессия потеряла блокировку, и логом уже может владеть другой узел) сообщает
  `currentLeader() == null`, поэтому `EngineReport.isLeader()` становится `false`
  сразу после отстранения, а не только после следующей неудачной записи.
  Отстранённый экземпляр может продолжать отвечать на запросы из состояния в
  памяти — направляйте трафик по `isLeader`.
- **Лидерская сессия поддерживается живой.** Каждые 15 с бэкенд «трогает»
  простаивающую лидерскую сессию и проверяет её advisory-lock, поэтому таймаут
  простоя на сервере или прокси длиннее этого её не завершает, а потеря
  блокировки замечается рано (`introspect()`/`isLeader` становятся `false`).
  `idle_session_timeout` или обрыв простоя на прокси **меньше 15 с** по-прежнему
  завершают сессию и отстраняют узел.
- **Ошибка отстранения называет причину.** `ERROR` `PostgresLogBackend[…] lost
  its advisory lock: <причина> (cause: <сообщение>, SQLState <код>); this
  instance is fenced …` говорит, какая проверка решила и почему: лидерская
  сессия пропала (с ошибкой, которая это показала), отдельная сессия видит, что
  блокировка больше не удерживается, или блокировку слишком долго не удавалось
  проверить. Если это обнаружила отдельная сессия (проба health-check'а), бэкенд
  отправляет один `SELECT 1` в лидерскую сессию с сетевым таймаутом 2 с, чтобы
  узнать настоящую причину: `57P05` — idle-session timeout, `57P01` —
  `pg_terminate_backend` администратора, `08xxx` — оборванный сокет, либо что
  сессия всё ещё отвечает, то есть блокировку сняли в живой сессии
  (`pg_advisory_unlock_all()`, `DISCARD ALL`, сброс сессии пулером). Каждое
  последующее `LeadershipLostException` несёт ту же причину в сообщении (`…
  leader session was lost (<причина>; cause: …)`) и ошибку как cause.
- **Достоверно потерянная блокировка отстраняет сразу, неподтверждаемая — через
  30 с.** Закрытое или прерванное сервером лидерское соединение (SQLState
  `08xxx`/`57Pxx`) либо проверка, показавшая, что блокировка не удерживается,
  отстраняют узел немедленно. Если падает сама проверка advisory-lock
  (отменённый запрос — например, при шквале `pg_cancel_backend` — или таймаут
  запроса), она повторяется, а затем перепроверяется через отдельное соединение
  из `DataSource` по pid лидерской сессии, не дольше 3 с вместе с получением
  соединения. Если не удалось и это, результат неопределённый и сразу узел не
  отстраняет; но если проверки остаются неопределёнными дольше 30 с без
  единого достоверного «удерживается» между ними, блокировка считается
  потерянной и узел отстраняется. На простаивающем узле проверяет только
  keepalive раз в 15 с, поэтому это занимает около 45–50 с. Для перепроверки
  `DataSource` должен уметь выдать одно дополнительное короткоживущее соединение.
- **Запись применяется только после успешной проверки блокировки в ней самой.**
  Каждая запись проверяет блокировку внутри своей транзакции на лидерской
  сессии; неопределённая проверка никогда её не пропускает. Запись (append), чья
  проверка блокировки упала, не применяется: она падает с «could not verify the
  advisory lock (statement failed: …); the write was not applied» с SQL-причиной
  внутри, и её можно повторить. Запись, отклонённая потому, что блокировка
  *потеряна*, падает с `LeadershipLostException` (наследник
  `IllegalStateException`) — тем же типом, которым движок отвечает на отклонённый
  append, каким бы узлом потеря ни была замечена первой.
- **Закрывайте отстранённый бэкенд.** Отстранение запрещает экземпляру писать,
  но не завершает его сессию. Узел, отстранённый потому, что блокировку не
  удалось подтвердить, может всё ещё держать её в Postgres, и standby будет
  получать отказ, пока вы не вызовете `backend.close()` (или пока соединение не
  умрёт). Закройте отстранённый бэкенд — и откройте новый, если этот узел должен
  снова бороться за лидерство.
- **Прерывания не отстраняют узел.** Все записи на лидерской сессии выполняются
  на одном выделенном платформенном потоке; вызывающие (включая виртуальные
  потоки) ждут его, не реагируя на прерывания (флаг прерывания восстанавливается
  после). Поэтому прерванный вызывающий не может закрыть сокет лидера.

Схема (создаётся при отсутствии):

```sql
CREATE SEQUENCE <table>_rid_seq;
CREATE TABLE <table> (
  row_id    BIGINT NOT NULL DEFAULT nextval('<table>_rid_seq'),
  type      TEXT   NOT NULL,
  payload   BYTEA  NOT NULL,
  ts_millis BIGINT NOT NULL,
  CONSTRAINT <table>_rid_pk PRIMARY KEY (row_id)
);
ALTER SEQUENCE <table>_rid_seq OWNED BY <table>.row_id;
CREATE INDEX <table>_leader_ix ON <table> (row_id) WHERE type = 'LogLeader';
```

- Конструктор берёт `pg_try_advisory_lock(key)`, где `key` — первые 8 байт
  SHA-256 от `schema + "." + tableName` (UTF-8)
  (схема — `current_schema()`, поэтому один и тот же id лога в двух схемах — это
  два лога с двумя лидерами; прежние версии брали ключ только от имени таблицы —
  см. [Несколько узлов](multi-node.md#выбор-бэкенда)) на выделенном
  соединении, удерживаемом до `close()`, **до** создания таблицы.
  Второй экземпляр, открывающий ту же таблицу, быстро падает с
  `IllegalStateException` («advisory lock») — в том числе когда узлы стартуют
  одновременно на совершенно новом логе, — а standby, не получивший блокировку,
  таблицу не создаёт. Соединение (и блокировка) освобождается, даже если
  конструирование падает на полпути.
- Последовательность и первичный ключ **названы явно** (префикс имени таблицы
  плюс его 64-битный хеш на основе SHA-256, если суффикс не влезает в 63 байта),
  а не оставлены на усмотрение
  Postgres: его неявные имена для `BIGSERIAL PRIMARY KEY` усечены за счёт имени
  таблицы, поэтому два лога с длинным общим префиксом имён получили бы одно и то
  же имя последовательности, и их одновременные `CREATE` столкнулись бы на
  `pg_class_relname_nsp_index`. Таблица, созданная более ранней версией,
  сохраняет неявные имена Postgres: они вычитываются из каталога, а не угадываются.
- Столбец `row_id` — внутренний идентификатор строки из последовательности, он нужен только для
  упорядочивания. Видимый движку clock хранится в самом событии: при добавлении
  это последний clock + 1, при `compact` — переданный как есть.
- **Лог, в котором clock идёт назад, отвергается** — так же, как его отвергает
  файловый бэкенд. Clock начинается с 0 и строго растёт в порядке `row_id`;
  вклеенные строки другой линии истории (заново вставленные старые строки,
  восстановление, пришитое к копии) это нарушают, а добавление после них выдало
  бы уже существующие clock и заставило бы восстановление принять живое
  состояние за устаревшее. Clock хранится в нагрузке, а не в столбце, поэтому
  проверка разделена: конструктор сравнивает clock последней строки с числом
  строк (на этом попадаются старые строки, вставленные в конец) — сначала
  через оценку по диапазону `row_id`, два поиска по первичному ключу, чего
  хватает для любого лога без пропусков в `row_id` (в том числе любого
  компактированного); точный `count(*)` нужен только логу с пропусками
  (добавления, упавшие после получения `row_id`), чей последний clock попадает
  в эти пропуски, — а каждое чтение диапазона проверяет, что clock в его окне строго
  растут — и на стыке порций, если чтение продолжает предыдущее, так что
  стартовое сканирование движка проверяет весь лог. Обе проверки отказывают
  закрыто. Проверка конструктора отказывает до какой-либо записи (`… is spliced
  or reordered: its last row … has clock …, but the table holds … rows; it is
  refused (nothing was changed)`). Проверка чтения сообщает `IllegalStateException:
  Log table … is spliced or reordered: row_id … (position …, …) has clock … but the
  previous row (row_id …, position …) has clock …, so the log is spliced or corrupt: reading
  stopped at row_id … and the log is refused. Stop every instance on this log and
  repair it before use`. Само
  чтение ничего не пишет, но движок захватывает лидерство до стартового
  сканирования, поэтому к этому моменту **его `LogLeader` уже добавлен** после
  испорченных строк. Остановите все экземпляры на этом логе, затем восстановите
  таблицу из резервной копии или архива либо удалите чужие строки (и этот
  `LogLeader`, если оставляете остальное).
- Чтения адресуют строки по **позиции** (`ORDER BY row_id OFFSET ?`), поэтому
  позиционная адресация переживает компактизацию (которая пересоздаёт таблицу).
  Порционное сканирование (старт движка, resume, снапшот: `getBetween(0, k)`,
  `getBetween(k, 2k)`, …) не платит за этот `OFFSET` на каждой порции: бэкенд
  запоминает `row_id`, на котором закончился предыдущий диапазон (и oid таблицы),
  и выбирает следующую порцию **по ключу** (`WHERE row_id > ? ORDER BY row_id
  LIMIT ?`), так что полный проход линеен. Прежние версии на каждой порции
  считали всю таблицу и пропускали строки до порции через `OFFSET` —
  квадратично (лог в миллион строк открывался минутами). Чтение, которое не
  продолжает запомненную строку, находит строки другой таблицы (её подменила
  компакция) или получает неполное окно, откатывается к варианту с подсчётом,
  описанному ниже.
- `getBetween` с подсчётом берёт проверку границ (число строк) и сами строки
  **одним запросом**, то есть под одним снимком (чтению по ключу подсчёт не
  нужен: полное окно само доказывает границу), поэтому конкурентный append/compact не
  может укоротить результат. Кроме того, чтения **повторяются**, если лог
  выглядит короче запрошенного диапазона: `compact` переименовывает живую таблицу
  и создаёт под тем же именем новую, и чтение, разрешившее это имя после подмены,
  но взявшее снимок до неё, иначе увидело бы таблицу без строк. Поэтому читатель
  видит либо весь лог до компактизации, либо весь лог после неё — но никогда
  пустой или недописанный; действительно выходящий за границы диапазон
  по-прежнему бросает `IndexOutOfBoundsException`. Чтения не берут блокировок
  таблицы, поэтому компактизация их не блокирует.
- `DataSource` внедряете вы (используйте пул — см. выше). Идентификаторы валидируются и
  ограничены по длине (63-байтовый `NAMEDATALEN` Postgres); зарезервированное
  ключевое слово SQL (например, `user`, `order`) как имя таблицы отклоняется с
  `IllegalArgumentException`.
- `compact` переименовывает старую таблицу в `<table>_archived_<millis>` —
  вместе с её последовательностью, индексом первичного ключа и индексом
  `LogLeader`, чтобы новая живая
  таблица могла занять свои имена, а `DROP TABLE` унёс все её объекты с собой;
  `purgeArchives` удаляет все такие таблицы, кроме новейших (на лидерской сессии,
  с той же защитой от отстранённого лидера, что и любая запись). Прежние версии
  архивы Postgres никогда не удаляли. Как и в файловом бэкенде, штамп — это
  настенные часы лидера, но не меньше наибольшего существующего штампа архива + 1,
  поэтому архив, записанный прежним лидером с убежавшими вперёд часами, не может
  обойти новейший — и заставить `purgeArchives` удалить его; штамп, опережающий
  часы более чем на 100 лет, не принимается на веру (пишется `WARN`, архив
  считается самым старым). `purgeArchives` удаляет лишние архивы **начиная со
  старейших, по 50 в транзакции**: каждая удалённая таблица держит свои
  блокировки (таблица, последовательность, индекс, TOAST) до коммита, поэтому
  одна транзакция на тысячи архивов упала бы с «out of shared memory»
  (`max_locks_per_transaction`) и, откатываясь целиком, никогда бы не
  продвигалась. Закоммиченные пакеты остаются удалёнными, даже если следующий
  пакет упадёт.
- Архив принадлежит логу по **имени и метке**: `compact` в той же транзакции,
  что и переименование, ставит архиву комментарий таблицы
  `fom archive of <table>`, а `purgeArchives` удаляет только таблицы текущей
  схемы, чьё имя в точности совпадает с именем архива, которое этот лог выводит
  для их штампа, **и** которые несут комментарий этого лога. Длинные имена
  таблиц сокращаются до префикса плюс хеш, поэтому одного совпадения имени мало
  для доказательства владения; прежние версии использовали там слабый
  (полиномиальный) хеш и могли вывести одинаковые имена архивов,
  последовательностей и индексов для двух длинных id логов — и `purgeArchives`
  одного лога мог удалить архивы другого. Архивы, записанные до этой версии,
  комментария не имеют и теперь **никогда не удаляются**: удалите их вручную или
  пометьте (`COMMENT ON TABLE <archive> IS 'fom archive of <table>'`), чтобы
  вернуть их под `purgeArchives`. Пометка помогает только для **коротких**
  имён таблиц, у которых имя архива `<table>_archived_<millis>` укладывается в
  лимит Postgres в 63 байта без сокращения (имена таблиц примерно до 40 байт):
  у более длинных имён старые архивы несут в имени старый хеш, который никогда
  не совпадает с именем, выводимым этой версией, так что даже помеченный архив
  не будет найден — **удаляйте такие вручную**. Не снимайте комментарий с
  архива, который должен удаляться.

!!! warning "Компакция переименовывает живую таблицу — логическая репликация / CDC"
    `compact` заменяет живую таблицу новой под тем же именем; публикация,
    привязанная к старой таблице, уходит вместе с архивом. См.
    [Чтение лога через CDC](#consuming-the-log-with-cdc) ниже.

- `append` перепроверяет лидерство **внутри своей транзакции** и по логу, а не по
  закэшированному полю, за **барьером записи**: сначала берётся
  `LOCK TABLE <table> IN SHARE ROW EXCLUSIVE MODE` (компакция берёт
  `ACCESS EXCLUSIVE`). Этот режим конфликтует с `INSERT`/`UPDATE` любой другой
  сессии, но не с чтением, поэтому, когда он получен, любая другая запись в
  таблицу либо уже закоммичена — и видна проверке, — либо ждёт конца этой
  транзакции. Барьер — первый оператор транзакции, а сама транзакция идёт на
  `READ COMMITTED` при любом настроенном умолчании (см. пункт об изоляции выше).
  Затем во вставку вшита проверка: после новейшей известной этому
  экземпляру строки нет ни одной строки — в виде
  `COALESCE((SELECT max(row_id) FROM <table>), ?) <= ?`, на что Postgres при
  любом плане отвечает одним шагом назад по первичному ключу. (Прежние версии
  писали её как `NOT EXISTS (… WHERE row_id > ?)`: как только pgjdbc
  подготавливал запрос на сервере и Postgres переходил на generic-план, это
  становилось последовательным сканированием всего лога на **каждом** append.) Экземпляр, у которого лог забрали на
  ходу — появилась строка `LogLeader` с именем другого экземпляра, — получает
  `Optional.empty()` уже на следующем `append`, а не только после перезапуска;
  чужие строки, не являющиеся захватом, дописываются после, с часами больше
  их часов. Без барьера `LogLeader`, вставленный другой сессией, но ещё не
  закоммиченный, был невидим для проверки: append старого лидера получал больший
  `row_id`, переносил свою отметку за этот захват и продолжал писать (а захват
  дублировал его часы). Advisory-lock и так разводит узлы этой версии; барьер
  закрывает писателей, которых блокировка не видит, — узел версии с другим
  ключом блокировки при rolling-обновлении (см.
  [Обновления](../concepts/idempotent-restart.md#upgrades)), блокировку,
  отпущенную на живой сессии, ручной `INSERT`. Таблицу он ждёт не дольше 10 с
  (запись, не дождавшаяся её, падает и не применяется); ручной
  `VACUUM`/`ANALYZE` или autovacuum против wraparound на таблице лога задерживают
  её на всё своё время (обычный autovacuum сам отменяется через
  `deadlock_timeout`). При отказе заново читается, кто же лидер, так что
  `introspect()`/`isLeader` перестают заявлять лидерство, которого у экземпляра
  больше нет; вернуть лог себе он всё ещё может документированным способом —
  записав свой `LogLeader`. `compact` тоже проверяет последний `LogLeader` под
  своей блокировкой и отказывает (`IllegalStateException`, ничего не записано),
  если в логе есть строки, которых этот экземпляр не видел: снапшот
  планировался без них.
- **Пропускная способность append.** Append'ы **сериализованы**: все записи
  бэкенда идут по его единственному лидерскому соединению одна за другой, и
  **каждое событие — отдельная транзакция**: проверка блокировки (`pg_locks`),
  защищённый `INSERT` с пустой заглушкой вместо payload, `UPDATE`, записывающий в
  эту строку сериализованное событие, и `COMMIT` (один сброс WAL). Ни пакетной
  записи, ни group commit между событиями нет, так что пропускная способность
  ограничена задержкой round trip до Postgres плюс задержкой коммита, а не
  числом пишущих процессов или потоков. Каждый append ждёт, пока его коммит
  станет долговечным, поэтому потолок — задержка коммита (`fsync` WAL) вашего
  диска: при `synchronous_commit = on` на обычных дисках рассчитывайте на
  **несколько сотен append/с** (полевой тест намерил 300–400/с; около 1 400/с с
  `synchronous_commit = off`, ценой потери последних коммитов при падении
  сервера). ~2 000 append/с (~0,5 мс на один), намеренные на локальном
  контейнере Postgres 16 (Testcontainers, настройки по умолчанию), отражают
  дешёвые сбросы WAL там, и планировать по ним не стоит. По сети добавляйте
  RTT на каждый round trip (5 round trip на append). Каждый `UPDATE` к тому же оставляет на событие мёртвую
  версию строки, которую убирает autovacuum. Учитывайте это, если процессы
  пишут много событий в секунду: лог рассчитан на результаты инициализации и
  переходы состояний, а не на высокочастотный поток событий.
- `compact` отказывает с `LeadershipLostException` (наследник
  `IllegalStateException`), ничего не меняя, если последний `LogLeader` в логе
  называет другой экземпляр: отстранённый лидер не должен вернуть себе лог,
  записав снимком свой `LogLeader` в его начало.
- `compact` берёт блокировку таблицы `ACCESS EXCLUSIVE` с `NOWAIT`, повторяя
  попытки до 5 с, а не встаёт за ней в очередь. Пока таблицей пользуется другая
  сессия (отчётный запрос, `pg_dump`), читатели и `introspect()` не блокируются
  за компактизацией; если таблица остаётся занятой 5 с, компактизация падает.
- `compact` **повторяет временные конфликты**: её `RENAME`/`CREATE` обновляют
  строки каталога, которые параллельная миграция может обновлять тоже, не
  разделяя с ней ни одной блокировки таблицы (обычный пример — `GRANT … ON ALL
  TABLES IN SCHEMA` в открытой транзакции), и Postgres роняет второго писателя с
  `XX000` "tuple concurrently updated", взаимоблокировкой (`40P01`) или ошибкой
  сериализации (`40001`). Каждая из них откатывает всю компактизацию, поэтому она
  повторяется — до 5 попыток с удваивающейся паузой от 50 мс (в журнал на уровне
  `WARN`); после этого падает, ничего не применив.
- **Захватив таблицу, компактизация не ждёт ни одной блокировки дольше 1 с.**
  Сразу после блокировки `ACCESS EXCLUSIVE` она выполняет `SET LOCAL
  lock_timeout = '1000ms'` до конца своей транзакции. Без этого `RENAME` за
  открытой блокировкой каталога у миграции (тот же незакоммиченный `GRANT … ON
  ALL TABLES IN SCHEMA`) ждал бы конца миграции, **удерживая блокировку
  таблицы**, и все читатели живого лога (`getBetween`, `introspect()`,
  health-check'и) стояли бы, пока миграция открыта. Теперь ожидание падает с
  `55P03` (lock_not_available), попытка откатывается и отпускает таблицу и
  повторяется, как конфликты выше. Читатели блокируются не дольше примерно 1 с
  на попытку; миграция, открытая дольше всех 5 попыток (около 6 с), роняет
  компактизацию, ничего не применив, — сделайте снапшот позже. Собственный
  `55P03` блокировки таблицы (таблица занята 5 с) не повторяется.

### Режима только для чтения нет { #no-read-only-mode }

Открыть лог только для чтения нельзя. `PostgresLogBackend` при открытии
отказывается работать с hot standby или read-only-сессией
(`IllegalStateException`, «the database is a read-only server (hot standby?)»)
и берёт advisory lock лога в конструкторе — поэтому открыть его на таблице,
которой пользуется работающий движок, не получится: он сразу упадёт, а не станет
читателем. `fom-log` (`inspect`, `events`, `diagnose`, `compact`) принимает
только **файлы** `.bin`. Чтобы посмотреть живой лог Postgres, делайте запросы к
таблице напрямую: `type` и `ts_millis` — обычные столбцы, а `payload`
декодируется, как описано в [разделе о CDC](#consuming-the-log-with-cdc) ниже
(Java-сериализация `LogEvent`, всегда под `ObjectInputFilters.logPayload()`).
Запрос работает и на реплике.

### Чтение лога через CDC / логическое декодирование { #consuming-the-log-with-cdc }

Таблицу лога можно выгружать логической репликацией, Debezium или другим
CDC-инструментом — например, для журнала аудита. Что увидит такой потребитель:

- **Два изменения на событие.** Каждое добавление — одна транзакция, которая
  делает `INSERT` строки с **пустым** `payload` (настоящие в ней только `row_id`,
  `type` и `ts_millis`), а затем `UPDATE` этой строки с нагрузкой. Пропускайте
  `INSERT` и берите события из `UPDATE` (при `REPLICA IDENTITY` по умолчанию
  новая строка несёт все столбцы). Упавшее или отклонённое добавление
  откатывается и ничего не порождает, поэтому в `row_id` бывают пропуски.
- **Нагрузка — Java-сериализация** записи `LogEvent` (`io.fom.log.*` из
  `fom-core`), не JSON и не формат вашего `SerDe`: пользовательское состояние
  внутри `LogInitialized` — это `byte[]`, выданный вашим `SerDe`. Декодируйте
  с `fom-core` в classpath и, раз байты приходят из базы, **всегда** с
  allowlist'ом движка:
  `ObjectInputStream in = …; in.setObjectInputFilter(ObjectInputFilters.logPayload());`
  (см. [Безопасность](../security.md)). Clock события — внутри нагрузки; столбец
  `type` — простое имя класса, удобно для фильтрации до декодирования.
- **Компакция переписывает таблицу.** `compact` переименовывает живую таблицу
  в `<table>_archived_<millis>`, создаёт новую под старым именем и пишет в неё
  [снапшот](../concepts/snapshots.md) (снова `INSERT` + `UPDATE` на событие),
  всё одной транзакцией. Сохранённые `LogChangeGraph`/`LogInitialized`
  **порождаются заново с теми же clock**, что у них были, `LogLeader` лидера
  идёт с clock `0`, и лишь замыкающие `LogTrigger`/`LogPaused`/`LogSnapshot`
  получают новые clock. Потребитель поэтому видит пачку событий, которые
  (в основном) уже видел, в таблице с новым oid и `row_id`, начинающимися с 1.
  Дедуплицируйте по clock (уже обработанный clock — повторно выданная копия;
  `LogSnapshot` отмечает конец пачки) и ничего не завязывайте на `row_id`.
- **Публикации следуют за oid.** Публикация, созданная `FOR TABLE <table>`,
  привязана к oid таблицы, поэтому после первой компакции она **уходит вместе
  с архивом** и молча перестаёт видеть живой лог. Публикуйте
  `FOR TABLES IN SCHEMA <schema>` (Postgres 15+; архивы тоже попадут в
  публикацию — отфильтруйте их по имени на стороне потребителя) или заново
  добавляйте живую таблицу (`ALTER PUBLICATION … ADD TABLE <table>`) после
  каждой компакции. То же касается прав, триггеров и политик row-level
  security, вручную навешенных на живую таблицу: они остаются на архиве.

### Необходимые привилегии { #required-privileges }

Роли, под которой подключается `DataSource`, нужны:

| Когда | Привилегии |
|---|---|
| Создание **нового** лога | `CREATE` на схему (таблица, её последовательность, индекс первичного ключа и индекс `LogLeader` создаются при первом открытии) |
| Первое открытие таблицы, созданной прежней версией | владение таблицей, чтобы добавить индекс `LogLeader`; без него открытие пишет `WARN` и работает без индекса |
| Обычная работа (открытие, чтение, добавление) | `SELECT`, `INSERT` и `UPDATE` на таблицу лога — каждое добавление вставляет строку-заглушку, а затем `UPDATE`-ит её нагрузку — плюс `USAGE` на её последовательность (`<table>_rid_seq`); `LOCK TABLE … IN SHARE ROW EXCLUSIVE MODE` покрывается `UPDATE` |
| `compact` / снапшоты, `purgeArchives` | **владение** таблицей (а значит, её последовательностью и индексом): компактизация делает им `ALTER … RENAME`, ставит `COMMENT` на архив и создаёт новую живую таблицу (`CREATE` на схему); `purgeArchives` делает `DROP` архивов |
| Интроспекция | `SELECT` на `pg_locks` (по умолчанию выдан `PUBLIC`) |

`DELETE` и `TRUNCATE` не нужны никогда; при меньших правах операция падает на
первом же операторе. Роль, которая может открыть лог, но не владеет таблицей,
работает до первого снапшота, который падает с "must be owner of table".
Компактизация создаёт новую живую таблицу, поэтому гранты, выданные на таблицу
вручную, остаются на архиве (см. предупреждение выше): запускайте бэкенд от
владельца таблицы, а не полагайтесь на гранты на таблицу.

!!! warning "Row-level security"
    Бэкенд рассчитывает видеть **все** строки таблицы лога. Если на ней включён
    row-level security (и роль не владелец и не `BYPASSRLS`, либо задан
    `FORCE ROW LEVEL SECURITY`), политики должны давать роли видеть все строки:
    политика, скрывающая часть, заставляет бэкенд читать **обрезанный лог** —
    восстановление заново инициализирует скрытые процессы, добавления
    продолжаются после последнего видимого clock, а снапшоты уносят скрытые строки
    в архив. Не включайте RLS на таблице лога; изолируйте тенантов отдельными
    таблицами или схемами лога (см. [Безопасность](../security.md)).

!!! warning "Журналирование запросов копирует лог в журнал сервера"
    Каждое добавление пишет сериализованную нагрузку события — состояние
    процесса, а для `LogChangeGraph` и `param` каждого узла — как параметр
    привязки `UPDATE` (компактизация так же пишет весь снапшот). При
    `log_statement = 'mod'` или `'all'`, `log_min_duration_statement` либо
    `pgaudit` с `pgaudit.log_parameter = on` Postgres пишет эти параметры (hex
    `bytea`) в **журнал сервера**, а их длину ограничивает только
    `log_parameter_max_length` (по умолчанию `-1`: без ограничения). Это вторая,
    неуправляемая копия данных: снапшоты и `purgeArchives` до неё не достают.
    Для роли fom задайте `log_parameter_max_length = 0` (или небольшое значение)
    и не включайте `pgaudit.log_parameter` — например, `ALTER ROLE fom SET
    log_parameter_max_length = 0`, — либо держите журнал сервера под тем же
    режимом хранения, что и таблицу лога (см.
    [Безопасность](../security.md#data-retention)).

!!! note "Testcontainers"
    Интеграционные тесты `fom-jdbc` работают против реального Postgres через
    Testcontainers и потому требуют демона Docker. `PostgresLogBackendTest`
    прогоняет общий контракт бэкенда плюс тесты advisory-lock/reopen.

## Свой бэкенд

Реализуйте `io.fom.log.LogBackend` и соблюдайте
[контракт](../concepts/the-log.md#spi-logbackend). Чтобы получить тесты
инвариантов бесплатно, унаследуйте общий `LogBackendContractTest` (публикуется в
`fom-test`) — см. [Тестирование](testing.md). Его случай
`a_deposed_leaders_append_is_refused_or_fails_and_is_never_applied` принимает
**оба** варианта поведения на записи отстранённого лидера — `Optional.empty()`
или брошенное `LeadershipLostException` — и требует, чтобы в обоих случаях ничего
не было записано. Особенно важно правильно
обращаться с clock'ами — на них держатся [Sid'ы](../concepts/sid-and-clock.md):

- clock'и имеют тип `long`: храните их в 64-битном столбце или поле, а не в `int`;
- при `append` назначайте `clock = clock последнего события + 1` (`0` в пустом
  логе) через `LogClocks.nextClock(lastEvent)` (возвращает `long`) и
  `LogClocks.withClock` — а не `length()`, который после компакции отличается;
- в `compact` сохраняйте clock'и переданных событий и отклоняйте clock'и, которые
  не строго возрастают (`LogClocks.requireIncreasingClocks` бросает
  `IllegalArgumentException`); последующие добавления продолжают отсчёт после
  наибольшего;
- `get`/`getBetween` по-прежнему адресуют события по позиции `[0, length())`;
  позиции остаются `int`.

**Append должен переживать прерванных вызывающих.** Движок выполняет процессы в
виртуальных потоках и прерывает их (по таймаутам, при отмене, при остановке),
поэтому append может начаться с уже выставленным флагом прерывания или быть
прерван посередине. Это может провалить *этот* append, но не должно ломать лог
для всех остальных: никакого навсегда закрытого канала или соединения, никакой
недописанной записи, за которой окажется следующий append. Снимайте флаг на время
блокирующего ввода-вывода и восстанавливайте его после, а то, что закрыло
прерывание, открывайте заново (файловый бэкенд делает и то и другое; Postgres
восстанавливает флаг и сохраняет сокет открытым). Контрактный тест проверяет это
случаями `an_interrupted_caller_does_not_break_the_log` и
`interrupting_a_virtual_thread_mid_append_does_not_break_the_log`.

**То, как `append` сообщает о сбое, определяет, что движок сделает с процессом.**
Возможных исходов ровно четыре:

| `append` … | Движок … |
|---|---|
| возвращает `Optional.empty()` | **Окончательно.** Лидер — кто-то другой: процесс уходит в `Dead` с `LeadershipLostException`, которое движок формирует сам, без повторов. |
| бросает `io.fom.api.LeadershipLostException` | **Окончательно**, ровно как отказ выше, — для бэкенда, который узнаёт об этом через сбой (сорванный lock, потерянный lease). Узел сообщает сообщение именно вашего исключения. |
| бросает `IllegalArgumentException` | **Окончательно.** Это событие сохранить нельзя никогда (например, оно превышает ваши лимиты размера): процесс уходит в `Dead` с этим исключением. Называйте лимит в сообщении. |
| бросает что-либо ещё | **Временно.** Попытка повторяется с backoff'ом, пока не выйдет бюджет стадии (`initTimeout` / `loadTimeout`). |

В обоих окончательных случаях отклонённый результат init или load сразу уводит
процесс в `Dead`, а не повторяет попытки весь `initTimeout`. Поэтому
бросайте `LeadershipLostException` **только тогда, когда этот инстанс уже никогда
не сможет писать**: бэкенд, бросающий его на восстановимом условии («мой lease
*пока* не продлён»), убьёт каждый процесс, чей результат init или load попал в
это окно, — тогда как временное исключение просто повторили бы.

Если ваш бэкенд при `compact` сохраняет архивы (как файловый и Postgres), также
реализуйте `purgeArchives(int keepHistory)`: удаляйте все архивы, кроме
`keepHistory` новейших. Движок вызывает его после каждого запланированного
снапшота политики с конечным `keepHistory` (например,
`SnapshotPolicy.FixedInterval(interval, keepHistory)`), из
`SnapshotContext.purgeArchives` и из `Engine.purgeArchives`; при
`SnapshotPolicy.KEEP_ALL` по умолчанию он не вызывается вовсе. Больше нигде (в
том числе в `compact`) архивы не удаляйте: хранение выбирает вызывающий. Реализация по умолчанию ничего не делает, так
что без неё архивы никогда не удаляются. Давайте каждому архиву идентификатор,
**уникальный для каждого снапшота** и упорядочивающий их по возрасту: файловый
бэкенд использует `<name>.archived.<millis>`, Postgres —
`<table>_archived_<millis>`. Именно это позволяет `purgeArchives` отличить
`keepHistory` новейших архивов от остальных и удалить только остальные.
Отклоняйте `keepHistory < 0` через `IllegalArgumentException`, а `0` трактуйте
как «удалить все». См. [Снапшоты](../concepts/snapshots.md#архивы).
